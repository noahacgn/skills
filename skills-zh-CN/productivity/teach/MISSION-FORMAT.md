# MISSION.md 格式规范

`MISSION.md` 存放在工作区根目录下。它记录了用户学习该主题的*根本动机*。教学过程中的每一项决策——接下来教什么、呈现哪些资源、设计哪些练习——都应能回溯到该文档。

## 模板

```md
# 使命目标: {主题}

## 为什么学 (Why)
{1-3 句话。用户所追求的具体的现实世界目标。掌握这项技能后，他们的生活或工作会发生什么改变？避免诸如“理解 X”之类的抽象表达——深挖其背后的实际成效。}

## 成功的标志 (Success looks like)
- {用户将能够做到的具体、可观察的事情}
- {另一项具体成果}
- {…}

## 限制与约束 (Constraints)
- {时间、预算、既有承诺、学习偏好等任何制约方案的因素}

## 不在范围内 (Out of scope)
- {用户明确表示当前不想涉足的相邻主题——保护最近发展区}
```

## 编写规则

- **每个工作区对应唯一一个使命。** 若用户想要学习两门毫不相干的内容，应当拆分为两个独立工作区。
- **具体胜于抽象。** “在 10 月前完成半程马拉松”远好于“变得更健康”；“为我的团队交付一个 Rust CLI 工具”远好于“学习 Rust”。
- **针对模糊表述深挖澄清。** 若用户无法清晰阐述原因，在落笔前对其进行深入访谈。一份糟糕的使命定义比没有定义更具危害。
- **随着现实情况变化及时修订。** 使命会演变。当用户的目标发生转移时，更新该文件——切勿让过时的使命继续指导未来的会话。
- **保持简短。** 若 `MISSION.md` 超过了一屏的长度，它就失去了指南针的意义，变成了冗长的执行计划。
