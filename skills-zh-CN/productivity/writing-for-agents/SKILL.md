为供 Agent 读取的任何文档（包括 Skill、`AGENTS.md` / `CLAUDE.md`，或通过指针引用的文档）提供撰写参考。组织载体可能有所不同，但编写法则完全一致：相同的抓手让每次执行具有高度可预测性——让 Agent 在每次运行中采取相同的*执行流程*，而非每次产出机械死板的相同输出。

当你要编写的文档是 Skill 时，请参阅 [`SKILL-MECHANICS.md`](SKILL-MECHANICS.md) 了解 Frontmatter 编写、触发方式选择以及路由技能的设计。

## 上下文指针 (Context pointers)

**上下文指针 (context pointer)** 是保留在 Agent 上下文中的引用，它指定了某些上下文之外的参考资料，并编码了何时应当调阅它的触发条件。Skill 的 `description` 就是一种指针；`AGENTS.md` 中指向某篇文档的一行描述也是同类对象。指针的*措辞*（而非其指向的目标）决定了 Agent 何时调阅该资料——以及调阅的可靠程度。在一个措辞模糊的指针后放置必读材料是导致行为不稳定的根源：首先应当精简打磨措辞；只有在优化措辞仍无效时，才考虑内联该材料。

指针承担两项任务：声明材料是什么，并列出触发调阅该材料的**分支场景 (branches)**（分支是文档处理的不同用例，使得不同运行场景能走向不同的处理路径）。常驻上下文中的指针的每个词都会在每一轮对话中产生开销，因此它需要比正文经历更严苛的精简：

- **前置核心引导词 (Front-load the leading word)** —— 指针的触发效力主要取决于开头的字眼。
- **每个分支只保留一个触发条件。** 对同一分支换用同义词表述相当于将一个分支重复写了两次；应将其合并，仅保留真正独立不同的分支。
- **剔除正文中已包含的身份说明。**

## 两种开销负载 (The two loads)

你添加的每一篇文档和每一个指针，都在消耗以下两种预算之一：

- **上下文负载 (Context load)** —— 始终加载在 Agent 窗口中的内容对上下文造成的开销：如 `AGENTS.md` 中的一行、Skill 的描述，任何每一轮都驻留在上下文中的内容，无论其是否触发都会持续消耗 Token 和注意力。
- **认知负载 (Cognitive load)** —— 对人类造成的负担：需要记住存在哪些文档以及何时该调阅哪一篇。人类自身就是索引。这并非一种必须降到最低的成本——它是人类掌控力（Human Agency）的代价；应将其用在需要人类判断力的地方，在无需判断的地方坚决予以剔除。

仅通过指针访问的材料以指针自身的行数成本免除了上下文负载；而完全没有指针的材料则完全依赖人类的认知负载来调用。

## 信息层级 (Information hierarchy)

一份文档由两类内容构建而成——**步骤 (steps)**（Agent 按序执行的动作）和**参考 (reference)**（按需查阅的定义、规则、事实）——它们可以自由混合：全步骤（配方型）、全参考（审查规则型、本 Skill），或两者兼有。核心决策在于将每一部分放置在**信息层级**的哪个梯级上（按 Agent 对材料的即时需求程度由高到低排序）：

1. **文件内步骤 (In-file step)** —— 核心层级：Agent 按序执行的具体动作。
2. **文件内参考 (In-file reference)** —— 按需查阅。通常是完全并列平铺的规则集合（例如评审的所有规则平铺在一层）——这是合理的组织方式，并非代码异味（code smell）。
3. **披露式参考 (Disclosed reference)** —— 剥离到独立文件中，通过上下文指针进行索引，仅当指针触发时才加载。涵盖同目录下的同级文件，直至任意文档均可指向的完全外部参考资料。

向下推送的内容过少会导致顶层臃肿；推送过多则会隐藏 Agent 实际需要的材料。把握这种张力是设计的核心。

**渐进式披露 (Progressive disclosure)** 是沿着梯级向下移动的操作——移出主文件并隐藏在指针之后——以保证顶层保持清晰易读。这不仅是一项 Token 优化措施，更是保护信息层级的关键手段。分支判定是检验披露的最佳测试：将所有分支都需要的通用内容内联，将仅有部分分支涉及的内容推到指针之后。当文档包含步骤时，本应披露的内联参考会淹没步骤，导致 Agent 能否关注到步骤变成概率事件——这是影响行为稳定性的关键因素，而不仅仅是可读性问题。

**就近组织 (Co-location)** 是文件内的搭配原则：层级梯子决定了一块内容*下沉多深*，而就近组织决定了它落位后*与什么放在一起*。将一个概念的定义、规则和注意事项集中在一个标题下，而非四处分散，这样阅读一部分就能自然带出其相邻内容。检验标准：文档读起来应当像是为 Agent 编写的技术文档——聚合的内容具备这种质感；分散的内容则不然。（这与内容重复不同：重复是在两处表达相同含义；分散则是将单一含义割裂到多处。）

**内容蔓延 (Sprawl)** 是此处的典型失效模式：文档篇幅过长，即使每一行都是有效且唯一的。过量的内容会稀释注意力，且每增加一行都意味着多了一处维护成本。解决之道正是利用信息梯级：将参考资料披露到指针后，并按分支或执行顺序进行拆分，使每条路径仅承载其所需的内容。

## 步骤与完成准则 (Steps and completion criteria)

每个步骤都应当以一个**完成准则 (completion criterion)** 结尾——即告知 Agent 该项工作已完成的明确条件。两项属性使其成为关键抓手：

- **明确性 (Clarity)** —— Agent 能否清晰分辨“已完成”与“未完成”？模糊的边界（如“达成共识”）容易诱发**过早完成 (premature completion)**：在步骤尚未真正完成时就提前收尾，注意力过早滑向“宣告完成”。后续可见的步骤（**完成后的后续步骤 / post-completion steps**）会产生向后的拉扯力；而准则的明确性则是抵抗这种拉扯的阻力。防御顺序：**首先精准锐化边界**（局部且低成本）；只有在其具有不可化简的模糊性*且*你观察到了草率收尾的倾向时，才通过拆分执行序列来隐藏后续步骤——而隐藏只有跨越真实的上下文边界（如交接文档或派发子 Agent）才有效；内联调用仍会将后续步骤保留在上下文中，起不到隔离作用。
- **严格度 (Demand)** —— 它要求达到的深度。“确认每个被修改的模型都已核对”相比“输出一份变更列表”更能强制执行彻底的工作。严格度驱动**深入探究 (legwork)**——Agent 在工作内部开展的深入调研，蕴含在措辞要求之中，而非写成单独的步骤——且它不受步骤形式的局限：“应用每一条规则”对平铺的参考资料具有同样的约束力，正如“完成每一个步骤”约束序列一样，这正是全参考型文档依然能具备详尽执行标准的原因。

最有力的准则应当既具备可验证性，又具备穷尽性。

## 何时进行拆分 (When to split)

将一份文档拆分为两份会消耗两种负载之一，因此只有当收益明确时才进行拆分：

- **按顺序拆分 (By sequence)** —— 当后续步骤诱使 Agent 草率对待当前步骤时，拆分该步骤序列。将其移出视线能促使 Agent 在当前任务上进行更深入的探究。警惕反向操作：合并序列会让每个步骤暴露在后续步骤的拉扯中，容易引发过早完成。
- **按触发方式拆分 (By invocation)** —— 属于 Skill 特定的拆分：详见 [`SKILL-MECHANICS.md`](SKILL-MECHANICS.md)。

## 引导词 (Leading words)

**引导词 (leading word)** 是模型预训练知识中已经存在的紧凑概念，Agent 在执行文档时会借助其进行思考（如 *lesson*、*fog of war*、*tracer bullets*）。以单个词元（Token）的形式重复使用，绝不展开为整句，它能沉淀为分布式的定义，并通过调动模型既有的先验知识，以极少的 Token 锚定整片行为逻辑。自创术语在定义清晰的前提下也能生效，但自创词无法激活先验知识——你在定义它时所付出的 Token 成本，预训练词能免费提供；优先选用既有词汇。

它具有双重锚定效应。在正文中起到*执行锚定*：每次该词出现时，Agent 都会调动相同的行为模式；在平铺的参考资料中，它将注意力聚焦在一类需要关注的事物上。在指针中起到*触发锚定*：当相同的词汇贯穿在你的提示词、文档和代码库中时，Agent 会将这种通用语言与参考资料关联起来，从而更可靠地调阅它。

善于寻找使用引导词进行重构的机会。在三处详述的三联表述、指针花费一整句话表达的单一构想——都是应当浓缩为单个词元的段落：

- “快速、确定性、低开销” → *紧凑 (tight)*（*紧凑的*循环）。
- “一个你深信不疑的测试循环” → *飘红 (red)* —— 将模糊的判断转化为二元的客观可观察状态（该循环在遇到 Bug 时能准确*飘红*，反之则否）。

你将获得双重收益：更少的 Token，以及供 Agent 挂载思考的更清晰抓手。应当假定每份文档都存在可以被引导词取代的冗余阐述——去把它们找出来。

**否定句 (Negation)** 是该抓手旁的典型失效模式：通过禁止性指令进行引导会将禁止的行为引入上下文，反而让其*更*容易被激活。*不要去想大象*，脑海中便全都是大象；否定词是一种较弱的修饰，很容易被强烈激活的核心概念所淹没，导致禁令反而被半理解为执行该行为的指令。应当提示**正面目标 (positive)**——直接声明目标行为（“编写单行注释”），使被禁止的行为根本不被提及。禁止性表述只有在作为无法正向表述的强硬护栏时才具备存在价值；即便如此，也应将其与正面目标搭配使用，使注意力落在该做的事情上。

## 文档精简与修剪 (Pruning)

- 将每个含义保持在**单一事实来源 (single source of truth)**：一处权威位置，使修改行为变成单处编辑。**重复 (Duplication)**——在多处表达相同含义——会增加维护成本和 Token 开销，并不恰当地拉高了该含义在信息层级中的显著性。（这与引导词有本质不同：引导词是有意重复词元，绝非重复含义。）
- **运行环境**同样是事实来源——`package.json` 中的脚本、配置文件、目录结构、`--help` 输出——重复陈述这些内容的文档实质上是**缓存 (cache)**：即一次查询结果的副本，只有在查询成本极其高昂时才值得付出其开销负载。只缓存 Agent 无法通过直接查看获知的内容：未成文的约定、选择背后的决策原因、配置文件无法体现的坑点。将单文件、单命令即可查询的事实留给环境自身，在那里它们永远不会过时。
- 逐行检查**相关性 (relevance)**：它是否依然影响文档的行为？一行内容失去相关性，要么是因为它从未真正对任务产生过实质影响（纯粹的论述，或是本应披露的分支），要么是因为随着其描述的行为或环境发生变化而过时。篇幅越短的文档越容易保持相关性。若缺乏精简纪律，文档最终的宿命就是**沉积物 (sediment)**：过时的层级不断堆积，因为新增显得安全而删除看似冒险，直到你必须向下深挖才能找到依然有效的内容。
- 逐句排查**空操作指令 (no-ops)**：一条模型默认就会遵循的指令只会白白消耗负载而无实际产出。检验标准——相比默认行为它是否改变了实际动作？——是相对于模型而言的，而非相对于读者：两个人对某句话是否是空操作产生分歧，实质上是对模型的默认表现存在分歧，应当通过实际运行文档来判定，而非空谈争论。当一句话未通过检验时，直接删除整句，而非修剪字词。该测试同样适用于检验引导词：一个过于微弱、无法改变默认行为的词（当 Agent 已经足够详尽时要求其*详尽一些*）就是一个空操作，其解决办法是换用更有力的词（如 *毫不留情/relentless*），而非改用其他手法。
