# 二度设计规范 (Design It Twice)

当用户希望为选定的深化候选模块探索替代接口方案时，采用这种并行子 Agent 协作模式。基于 Ousterhout 的“Design It Twice（二度设计）”理念——你的第一个构想大概率不是最优解。

依托 [SKILL.md](SKILL.md) 中的词汇体系——**模块**、**接口**、**缝隙**、**适配器**、**杠杆率**。

## 执行流程

### 1. 框定问题空间 (Frame the problem space)

在派发子 Agent 之前，面向用户编写一段关于选定候选模块的问题空间说明：

- 任何新接口必须满足的约束条件
- 它所依托的依赖项，以及这些依赖归属哪一类（参见 [DEEPENING.md](DEEPENING.md)）
- 粗略的代码草图以辅助说明约束——不是最终提案，仅用于使抽象约束具象化

将此内容展示给用户，随后立即推进到步骤 2。用户在阅读思考的同时，子 Agent 并行展开设计。

### 2. 派发子 Agent (Spawn sub-agents)

并行启动 3 个或更多子 Agent。每个 Agent 必须为深化后的模块产出**截然不同 (radically different)** 的接口设计。

为每个子 Agent 提供独立的技术任务书（文件路径、代码耦合细节、来自 [DEEPENING.md](DEEPENING.md) 的依赖类别、缝隙背后的内容）。该任务书独立于步骤 1 中面向用户的问题空间说明。为每个 Agent 设定不同的设计约束：

- Agent 1: “最小化接口——最多提供 1–3 个入口点。最大化单个入口点的杠杆率。”
- Agent 2: “最大化灵活性——支持丰富的业务用例与灵活扩展。”
- Agent 3: “针对最高频的调用方进行优化——使默认最常见用例变得极简。”
- Agent 4 (若适用): “围绕端口与适配器设计跨缝隙依赖。”

在任务书中同时包含 [SKILL.md](SKILL.md) 词汇体系与 `CONTEXT.md` 业务领域词汇，以便每个子 Agent 均能与架构语言及项目业务语言保持严格一致。

每个子 Agent 输出：

1. 接口定义（类型、方法、参数——外加不变式、时序要求、错误模式）
2. 展示调用方如何使用的调用示例代码
3. 实现层在缝隙后隐藏的具体复杂逻辑
4. 依赖处理策略与适配器设计（参见 [DEEPENING.md](DEEPENING.md)）
5. 权衡取舍——哪里杠杆率极高，哪里相对单薄

### 3. 呈现与对比 (Present and compare)

按顺序依次呈现各个设计方案以便用户充分吸收，随后通过论述对比它们。从**深度**（接口处的杠杆率）、**局部性**（变更集中在何处）以及**缝隙位置**三个维度进行横向对比。

对比完成后，给出你自己的主见推荐：你认为哪套方案最强健，理由是什么。若不同方案中的亮点可以有机结合，提出混合设计方案。保持鲜明观点——用户需要的是敏锐洞察，而非被动点单。
