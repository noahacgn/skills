# 代码库架构设计 (Codebase Design)

设计**深模块 (deep modules)**：在清晰的缝隙处，通过狭小的接口承载丰富深厚的行为，并通过该接口进行测试。在设计或重构代码的任何地方运用这套语言和原则。其目标是为调用方提供高杠杆率、为维护者提供高局部性，并为所有人提供卓越的可测试性。

## 术语表 (Glossary)

严格使用以下术语，切勿替换为“组件 (component)”、“服务 (service)”、“API”或“边界 (boundary)”。保持语言的一致性是本规范的核心价值。

**模块 (Module)**：任何具备接口和实现的载体。有意保持尺度中立：可以是一个函数、类、代码包或跨层切片。_避免使用_: 单元 (unit)、组件 (component)、服务 (service)。

**接口 (Interface)**：调用方为了正确使用该模块所必须知晓的全部内容：不仅包括类型签名，还包含不变式约束、调用时序约束、错误模式、必要配置以及性能特征。_避免使用_: API、签名 signature（范围过窄，它们仅指代类型层面的表象）。

**实现 (Implementation)**：模块内部的代码正文。与**适配器 (Adapter)** 有严格区分：一个实体可以是一个带有庞大实现的小型适配器（如 Postgres 仓储），也可以是一个带有微小实现的大型适配器（如内存 Fake）。当探讨的重点是缝隙时，使用“适配器”；其余场景使用“实现”。

**深度 (Depth)**：接口处的杠杆效率：调用方（或测试）每学习一个单位的接口所能调动的行为容量。当微小的接口背后承载着大量的复杂行为时，该模块就是**深模块 (deep)**；当接口的复杂度几乎与内部实现持平甚至倒挂时，该模块就是**浅模块 (shallow)**。

**缝隙 (Seam)** _(源自 Michael Feathers)_，无需在代码原处进行编辑即可改变其行为的位置；即模块接口所在的*物理位置*。在何处设置缝隙是一项独立的设计决策，与缝隙背后承载的内容截然不同。_避免使用_: 边界 boundary（与 DDD 的界限上下文混淆）。

**适配器 (Adapter)**：在缝隙处满足接口契约的具体实体。用于描述*角色定位*（填补哪个插槽），而非实质内容（内部的具体逻辑）。

**杠杆率 (Leverage)**：调用方从模块深度中获取的收益：每掌握一个单位的接口，就能获得更多的能力支撑。单次实现的投入将在 N 个调用点和 M 个测试中获得持续回报。

**局部性 (Locality)**：维护者从模块深度中获取的收益：变更、Bug、领域知识与校验逻辑高度集中在单一位置，而非扩散蔓延到各个调用方。修复一次，全处生效。

## 深模块 vs 浅模块 (Deep vs shallow)

**深模块 (Deep module)** = 极小的接口 + 丰富的内部实现：

```
┌─────────────────────┐
│      小接口         │  ← 方法极少，参数简洁
├─────────────────────┤
│                     │
│      深实现         │  ← 隐藏复杂的业务逻辑
│                     │
└─────────────────────┘
```

**浅模块 (Shallow module)** = 庞大的接口 + 单薄的实现（应予避免）：

```
┌─────────────────────────────────┐
│            大接口               │  ← 方法繁多，参数复杂
├─────────────────────────────────┤
│  薄实现                         │  ← 仅仅作为直接透传
└─────────────────────────────────┘
```

在设计接口时，持续自问：

- 我能否减少对外暴露的方法数量？
- 我能否简化调用参数？
- 我能否将更多复杂度封装隐藏在内部？

## 核心设计原则

- **深度是接口的属性，而非实现的属性。** 深模块内部完全可以由细小、可 mock、可插拔的内部组件组合而成，这些只是不属于对外接口的一部分。模块可以拥有**内部缝隙**（对其实现私有，供其专属测试使用）以及接口处的**外部缝隙**。
- **删除测试法 (The deletion test)。** 设想删除该模块。如果复杂度随之烟消云散，说明它此前只是一个冗余的透传层。如果复杂度重新散落蔓延到 N 个调用方之中，说明它确确实实承担了其应有的价值。
- **接口即测试暴露面 (The interface is the test surface)。** 调用方与测试穿越的是同一道缝隙。如果你需要穿透接口*深入内部*去测试，通常意味着该模块的形态设计有误。
- **单个适配器意味着假想的缝隙，两个适配器才代表真实的缝隙。** 除非在缝隙两侧确实存在可变行为，否则不要引入缝隙。

## 面向可测试性设计

优秀的接口让测试水到渠成：

1. **接收依赖，而非自行创建。**

   ```typescript
   // 易于测试
   function processOrder(order, paymentGateway) {}

   // 难以测试
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，而非产生副作用。**

   ```typescript
   // 易于测试
   function calculateDiscount(cart): Discount {}

   // 难以测试
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **极小的表面积。** 更少的方法 = 需要编写的测试更少。更少的参数 = 测试脚手架搭建更简单。

## 实体关系脉络

- 一个 **模块 (Module)** 拥有且仅拥有一个 **接口 (Interface)**（呈现给调用方与测试的面）。
- **深度 (Depth)** 是 **模块** 相对于其 **接口** 所度量的属性。
- **缝隙 (Seam)** 是 **模块** 的 **接口** 所在的位置。
- **适配器 (Adapter)** 驻留在 **缝隙** 处并满足 **接口** 的约束。
- **深度** 为调用方带来 **杠杆率 (Leverage)**，为维护者带来 **局部性 (Locality)**。

## 被摒弃的概念框架

- **以实现代码行数除以接口代码行数的比率来定义深度** (Ousterhout 原书观点)：这会诱导故意给实现注水以虚增行数。我们在此采用“深度即杠杆率”的定义。
- **将“接口”狭义理解为 TypeScript 的 `interface` 关键字或类的公有方法**：范围过窄，此处的接口涵盖调用方必须知晓的每一个客观事实。
- **“边界 (Boundary)”**：与 DDD 中的界限上下文冲突。一律使用 **缝隙 (seam)** 或 **接口 (interface)**。
