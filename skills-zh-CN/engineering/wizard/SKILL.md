# 交互式向导 (Wizard)

**向导 (wizard)** 是一个 Bash 脚本，它一步一步引导人类完成手动操作流程，这类流程手工操作极其繁琐，且每次都要向 AI 重新解释一遍同样令人头疼。它能自动打开每个 URL、明确指出需要点击并复制什么、捕获对应的值、将其写入正确的归属位置（`.env`、GitHub Secrets）、在每个阶段提供确认门禁，并显示还剩余多少个阶段。它可以用于配置第三方服务、运行一次性数据迁移，或推动项目从一个状态演进到另一个状态。

令人愉悦的用户体验已被 [template.sh](template.sh) 完美解决，分阶段进度展示、确认门禁、跨平台 URL 打开（包含 WSL 支持）、隐藏敏感凭据输入、幂等的 `.env` 更新写入、`gh secret`/`gh variable` 写入以及收尾摘要报告。**你的工作仅仅是界定流程范围并编写各个阶段。** `STAGES` 标记上方的代码库在每个向导中完全一致；这种一致性正是核心精髓，绝不要手动修改上方库代码。

向导默认是一次性的，为单次运行构建，保存在草稿目录或 `scripts/` 下，任务完成后即可删除。仅当用户希望将其作为留在仓库中的可重复配置流程时才提交到 Git。

## 执行流程

### 1. 界定操作流程范围 (Scope the procedure)

梳理出人类必须采取的每一个手动步骤，以及沿途捕获的每一个配置值。首先通读代码库，切勿在没有上下文的情况下生硬发问：

- 对于初始化配置：查阅 `.env`、`.env.example`、`.env.*`、`README`、`docker-compose*`、框架配置文件以及 `.github/workflows/*`（每个 `secrets.*` / `vars.*` 引用都是向导必须产出的值）。
- 对于迁移或状态切换：查阅当前状态、目标状态以及两者之间的不可逆操作。

随后向用户展示各个阶段的有序清单以及每个阶段产出的配置值，并请求确认，用户可能会添加、删除或调整顺序。

**完成标准：** 每个阶段按序命名，且针对每个捕获的配置值，你明确知晓 (a) 人类从何处获取它，(b) 它写入哪里（`.env`、GitHub Secret、两者兼有、或无需写入，部分阶段纯粹是动作操作），以及 (c) 它是否属于机密凭据（隐藏输入）还是公开配置。

### 2. 映射每个阶段的操作路径 (Map each stage's journey)

对于每个阶段，编写人类应当遵循的精确操作路径：打开哪个 URL、在那里做什么、目标值展示在何处、填入哪个环境变量，例如“控制台 → 开发者设置 → API 密钥 → 显示测试密钥 → 复制”。若你不确切了解当前的 UI 或具体命令，明确说明并向用户询问或查阅文档，绝不要凭空捏造可能不存在的步骤。

**完成标准：** 每个阶段均对应着陌生人拿来就能顺利照做执行的具体指引。

### 3. 编写向导脚本 (Author the wizard)

将 `template.sh` 复制到目标路径。将示例阶段替换为按依赖顺序排列的具体 `stage`。使用脚手架提供的辅助函数，`stage`、`say`/`step`、`open_url`、`ask`/`ask_secret`、`write_env`、`set_secret`/`set_var`、`pause`/`confirm`，并将 `TOTAL_STAGES` 设置为你编写的实际阶段总数。

严格遵循模板所设定的质量门槛：在要求输入某个配置值之前先自动打开对应 URL、机密凭据一律使用 `ask_secret`、所有需要持久化的配置值使用 `write_env`、仅将 CI 确实需要的配置通过 `set_secret` 写入、在执行任何不可逆操作前通过 `confirm` 提示确认。每个 `stage` 执行时会自动清屏，确保仅显示当前步骤，让每个阶段专注于单一任务，避免人类所需的信息被滚屏冲走。切勿修改标记上方的库代码。

### 4. 验证并交付 (Verify and hand off)

- 执行 `bash -n <script>` 进行语法检查；若环境可用，运行 `shellcheck`。
- 执行 `chmod +x <script>` 赋予执行权限。
- 切勿自行端到端直接运行它，它会打开浏览器并阻塞等待人工输入。通过静态检查进行验证：确保步骤 1 中的每个配置值均被捕获并准确落位在步骤 1 指定的位置，且每个 `set_secret` 命名严格与 CI 中的 `secrets.*` 引用一致。
- 告知用户如何运行该向导。若这是可重复使用的初始化路径，将其提交到 Git 并在 README 中进行链接，以便下一位开发者直接运行脚本而非向 AI 重复询问。
