当一个宽泛宏大的构想涌现时——它庞大到无法被单个 Agent 会话容纳，且笼罩在浓厚的迷雾中：从当前位置通往**最终目标 (destination)** 的路径尚不可见。寻路（Wayfinding）的本质在于探寻通往目标的道路，而非鲁莽地盲目冲锋。本技能在代码库的 Issue 追踪系统上将这条道路绘制为一张**共享地图 (shared map)**，随后逐一解决其中的**决策 Ticket**（其产出是决策结论，而非具体执行的编码切片），直至前进路线完全清晰。

每个任务的目标各不相同，定义目标是绘制地图的首要动作——它将直接塑造后续的每一个 Ticket。目标可能是一份供后续交接迭代的规格说明、启动规划前必须锁定的重大决策，或是就地开展的数据结构迁移改造。地图是领域中立的——工程开发、课程内容体系设计，任何契合该形态的复杂任务均可使用。

## 聚焦规划，而非直接动手编码 (Plan, don't do)

Wayfinder 默认定位为**规划**：每个 Ticket 解决一项决策，当路线完全清晰时地图即告完成——在有人着手执行具体编码之前，不再有任何悬而未决的决策。想要直接编码动手的冲动，通常意味着你已经抵达了地图的边缘，是时候交接进入实现阶段了。某项任务可以在其 **Notes** 中显式覆盖此规则（将具体执行纳入地图自身中），但在没有特殊约定的情况下，产出决策，而非可交付物。

## 使用具名名称进行引用 (Refer by name)

每张地图和每个 Ticket 都是一个 Issue，因而都拥有一个**具名名称**——即其标题。在面向人类的所有文本中（过程叙述、地图的“迄今决策”列表），始终使用其具名标题进行引用，绝不要裸露使用 ID、纯数字编号或 Slug。堆砌 `#42, #43, #44` 是无法快速阅读的；具名名称让人一目了然。ID 和 URL 并不会消失——名称本身包裹着其超链接——但它们应当置于名称*内部*，绝不能直接取代名称。

## 共享地图 (The Map)

地图是本代码库 Issue 追踪系统中的单个 Issue，打上 `wayfinder:map` 标签——这是权威的基准产物。其具体 Ticket 是地图的子 Issue。

地图是一份**索引**，而非大仓库。它列出已做出的决策并指向承载其详尽细节的具体 Ticket；每项决策只存在于唯一一个地方——即其对应的 Ticket 中——因此地图本身从不重复陈述细节，仅保留核心要点并提供跳转链接。

**地图、子 Ticket、阻塞关系以及前沿查询在物理上如何呈现取决于具体的 Issue 追踪系统。** 追踪系统应已配置。若未配置，请告知用户运行 `/setup-matt-pocock-skills`。查阅追踪配置文档的“寻路规划操作”小节了解本仓库的实现细节。若未配置追踪系统，默认采用本地 Markdown 模式。

### 地图正文结构

整张地图的低精度全貌，每个会话仅加载一次。未解决的 Open Ticket **不**直接写在正文中——它们是未关闭的子 Issue，通过查询检索。

```markdown
## 目标 (Destination)

## 备忘录 (Notes)

- [<已解决 Ticket 标题>](link) — <答案的一句话核心要点>
```

### Ticket 结构

每个 Ticket 是地图的**子 Issue**；追踪系统分配的 Issue ID 是其唯一标识。其正文即为核心问题，大小恰好适合单个 10 万 Token 的 Agent 会话：

```markdown
## 核心疑问 (Question)

<本 Ticket 致力于解决的核心决策或调查事项>
```

每个 Ticket 携带一个 `wayfinder:<type>` 标签——`research`、`prototype`、`grilling`、`task` 之一（参见 [Ticket 类型](#ticket-类型)）。

会话在开展任何具体工作前，**首先**将 Ticket 指派给自己以进行**认领 (Claim)**，以便并发运行的其他会话能够跳过它。被指派即代表被认领；处于 Open 且未指派状态的 Ticket 即为未被认领。

阻塞依赖采用追踪系统的**原生**依赖关联——这至关重要，因为它能在追踪系统自身的 UI 中将前沿边界*可视化渲染*出来，让人类无需打开地图正文就能直观看到哪些 Ticket 当前可被认领。只有缺乏原生依赖能力的追踪系统才回退到正文标记。当阻塞该 Ticket 的所有前置 Ticket 均已关闭时，该 Ticket **解除阻塞**；**前沿边界 (frontier)** 是指所有处于 Open、已解除阻塞且未被认领的子项——即已知领域的边缘。

答案不属于 Ticket 的初始正文——它在解决收尾时记录。解决过程中产出的资产文件通过超链接进行引用，而非直接粘贴到 Issue 中。

## Ticket 类型 (Ticket Types)

每个 Ticket 要么是 **HITL**（人工闭环 / Human In The Loop，与人类实时互动协作完成），要么是 **AFK**（由 Agent 独立离线驱动）。HITL Ticket 必须通过实时对话交流来解决；Agent 绝不能越俎代庖替人类作答（一个自己向自己提问并自己回答的盘问 Agent 破坏了该规则）。

- **调研类 (Research)** (AFK): 阅读官方文档、第三方 API 或知识库等本地资源，以挖掘某项决策所依赖的事实。由调用 Skill 工具并传入 `"research"` 的子 Agent 解决。当需要当前工作目录以外的外部知识时使用。
- **原型类 (Prototype)** (HITL): 制作一个廉价、粗糙但具体的具象产物来提升讨论保真度——提纲、草案、Stub，或通过调用 Skill 工具并传入 `"prototype"` 制作的 UI/逻辑代码。在 Issue 中链接原型资产。当“应该长什么样”或“应该表现出什么行为”是核心疑问时使用。
- **盘问类 (Grilling)** (HITL): 对话交流。最通用的默认形态。始终调用 Skill 工具两次，分别传入 `"grilling"` 与 `"domain-modeling"`。
- **任务类 (Task)** (HITL 或 AFK): 在做出*决策*前必须先行完成的手工操作——无需决策、原型或调研，但必须完成它讨论才能继续。例如注册第三方服务以便评估其 API、开通环境权限、搬移数据以便观察其形态。这是唯一定位为*执行操作*而非做出决策的类型——它的存在价值在于为后续决策扫清障碍，而非直接交付最终目标。Agent 能独立完成的尽量独立执行 (AFK)；否则向人类提供清晰的 Checklist (HITL)。操作完成后宣告解决；答案中记录执行了什么以及后续 Ticket 所依赖的事实产物（凭据位置、新生成的 URL、数据量等）。

## 战争迷雾 (Fog of war)

地图是*有意*保持不完备的：不要去绘制你当前尚看不清的领域。在活跃的 Ticket 之外笼罩着**战争迷雾 (fog of war)**——那些你预感到即将到来但由于前置问题尚未解决而无法精准锚定的决策与调查事项。解决一个 Ticket 会驱散其前方的迷雾，将现在可以精准描述的内容逐步毕业升级为全新的 Ticket——逐一推进，直至通向目标的路径完全清晰，不再遗留任何迷雾。

地图的 **尚未明确的领域 (Not yet specified)** 正是记录这种模糊远景的地方：推测可能涉及的问题、后续需要重新审视的领域。它是通向目标的未探索前沿——这里的所有内容都在项目范围之内，只是当前还不够锐利无法直接立项为 Ticket。根据视野的清晰程度自由简明或详尽记录；它同时作为协作人员了解本任务大方向的指路牌。

**何时作为迷雾记录，何时立项为 Ticket？** 检验标准在于你当前能否*精准陈述核心问题*——而*不是*你当前能否给出答案。

- **立项为 Ticket**：当问题已经足够清晰锐利——即使它当前被阻塞且你暂时无法着手。
- **归入尚未明确的领域**：当你尚无法精准清晰地表述该问题时。不要预先将迷雾强行切碎为 Ticket 粒度：迷雾比 Ticket 更粗犷，当探索前沿触达它时，一块迷雾可能会衍生为数个 Ticket，也可能完全不需要立项。

**尚未明确的领域**严格排除已敲定的决策（迄今决策）、已成为活跃 Ticket 的内容以及超出范围的事项。

## 不在范围内 (Out of scope)

迷雾只会在*通向目标的方向*聚集。最终目标锚定了任务范围，因此超出目标之外的工作属于**超出范围 (out of scope)**——它不是迷雾，也不属于“尚未明确的领域”。它在地图上拥有专属的 **不在范围内** 小节：记录你已明确在此次任务中排除的工作。决定其落位的是边界范围，而非清晰度。

超出范围的工作永远不会毕业为 Ticket——前沿推进在目标处便会停止——因此它只有在重新调整最终目标时才会重新回归，届时应作为一项全新的任务启动，而非继续恢复。

将某项内容判定为超出范围是一项范围界定动作，而非行进路线上的步骤。当一个已存在的 Ticket 被证实超出了目标范围时——可能是在初期绘制地图时范围界定有误，或随某个决策的解决而暴露出来——**关闭该 Ticket**（已关闭的 Ticket 明确脱离前沿边界），并在 **不在范围内** 小节中留下一行记录：核心要点及为何超出范围，并附带指向该已关闭 Ticket 的超链接。它绝不进入 **迄今决策**，后者仅记录实际走过的路线——范围边界并不是行进路线上的有效步骤。

## 调用方式 (Invocation)

支持两种模式。无论哪种模式，**单次会话中绝不要解决超过一个 Ticket**——调研类 (Research) Ticket 除外。

### 绘制地图 (Chart the map)

用户携带着一个粗略宽泛的构想调用。

1. **确立最终目标。** 调用 Skill 工具两次，分别传入 `"grilling"` 与 `"domain-modeling"`，以锁定本地图旨在探寻出的最终形态——Spec、关键决策还是架构改造。目标决定了边界范围，因此必须最先确立。
2. **广度优先勘察前沿。** 再次展开盘问，本次采用**广度优先 (breadth-first)**：在整个问题空间横向铺开而非深挖某个单点，梳理出所有未决决策以及当前可立即采取的第一步。**若此过程未发现任何迷雾**——通向目标的道路完全清晰，整个旅程小到单个会话即可搞定——你根本不需要地图。停下来询问用户希望如何推进。
3. **创建地图 Issue**（打上 `wayfinder:map` 标签）：填入目标与备忘录，迄今决策保持空白，将迷雾勾勒在“尚未明确的领域”中。
4. **将当前能够明确的问题创建为子 Ticket**，随后在**第二遍遍历中建立阻塞关联**（Issue 必须先具备 ID 才能相互引用）。依赖关联将它们划分为前沿边界和受阻项；当前尚无法精确描述的内容保留在迷雾中——即“尚未明确的领域”小节。
5. **触发调研子 Agent。** 针对刚刚创建的每个 `research` Ticket，并行启动调用 Skill 工具并传入 `"research"` 的子 Agent 展开调研，将调研成果保存在一次性 `research/<name>` 分支上，并在 Ticket 中附带上下文指针。
6. 收工——绘制地图是单个会话的全部工作；本会话不手动解决任何决策。

### 推进地图中的决策 (Work through the map)

用户携带地图调用（传入 URL 或编号）。指定 Ticket 是**可选的**——若未指定，由你挑选下一个决策，而非由用户挑选。

1. 加载**地图**——阅读低精度全貌，而非逐个加载所有 Ticket 正文。
2. 选定 Ticket。若用户指定了某一个，使用该 Ticket。否则按顺序认领前沿边界中的第一个 Ticket。**认领它**：在开展任何工作前将其指派给自己。
3. 解决它——**按需放大查看**：按需拉取相关或已关闭 Ticket 的完整正文；为 `## Notes` 区块中指定的技能调用 Skill 工具。如有疑问，调用 Skill 工具两次，分别传入 `"grilling"` 与 `"domain-modeling"`。
4. 记录解决结论：发表**解决结论评论**，**关闭**该 Issue，随后在地图的“迄今决策”中**追加上下文指针**。
5. 新增浮现出的新 Ticket（先创建后建立依赖）；将结论促成明确的任何迷雾毕业升级，并将毕业的内容从“尚未明确的领域”中清除，使其仅作为新 Ticket 存在。若结论表明某个 Ticket 超出了最终目标，**将其判定为超出范围**而非继续在路线上解决它。若决策推翻了地图的其他部分，相应更新或删除受影响的 Ticket。

用户可能会并行推进多个未受阻的 Ticket，因此要做好其他会话可能同时并发编辑追踪系统的准备。
