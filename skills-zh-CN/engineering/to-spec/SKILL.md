本技能提取当前对话上下文与代码库认知，产出一份完整的规格说明（Spec）。**不要**对用户发起新的访谈——仅综合提炼你已知的内容。

Issue 追踪系统与分类标签词汇表应已配置完毕。若未配置，请告知用户运行 `/setup-matt-pocock-skills`。

## 执行流程

1. 探索代码库以了解当前代码状态（若尚未执行）。在整篇 Spec 中严格使用项目的业务领域术语，并遵循所触碰区域的 ADR。

2. 规划用于测试该特性的代码缝隙（Seams）。优先复用既有缝隙而非新建。采用尽可能最高层次的缝隙。若必须引入新缝隙，提议在尽可能高的层级设置。代码库中的缝隙越少越好——理想数量是 1 个。

向用户确认这些缝隙是否符合其预期。

3. 使用下方模板编写 Spec，随后发布到项目的 Issue 追踪系统中。为其打上 `ready-for-agent` 分类定级标签——无需再进行额外的分类定级流程。

<spec-template>

## 问题陈述 (Problem Statement)

从用户视角描述当前遇到的具体问题。

## 解决方案 (Solution)

从用户视角描述该问题的解决方案。

## 用户故事 (User Stories)

详尽编号的用户故事列表。每个用户故事格式如下：

1. As an <角色/参与者>, I want a <功能特性>, so that <获得的业务收益>

<user-story-example>
1. As a 手机银行客户, I want to 在账户上查看实时余额, so that 我能对消费支出做出更明智的决策
</user-story-example>

用户故事列表应当极其详尽，穷尽该特性的所有方面。

## 实现决策 (Implementation Decisions)

已敲定的实现决策清单，可包含：

- 将构建/修改的具体模块
- 这些模块将被调整的接口契约
- 开发者明确的技术澄清点
- 架构决策
- 数据模型 Schema 变更
- API 契约定义
- 具体的交互行为

**切勿**包含具体的文件路径或大段代码片段。它们很容易迅速过时。

例外情况：若原型产出了能够比纯文本更精准表达决策的片段（状态机、Reducer、Schema、类型结构），可将其内联在相应决策中并简要注明源自原型。仅保留蕴含决策的关键精髓——而非可运行的完整演示。

## 测试决策 (Testing Decisions)

已敲定的测试决策清单，包含：

- 优质测试的标准阐述（仅测试外部可观察行为，不测试实现细节）
- 将测试哪些具体模块
- 测试的既有先例参考（即代码库中同类型的现有测试）

## 不在范围内 (Out of Scope)

明确声明本 Spec 不涉及的内容范围。

## 补充说明 (Further Notes)

关于该特性的任何其他补充备忘。

</spec-template>
