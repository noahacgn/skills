# 向 Matt 咨询 (Ask Matt)

你不必强行记住每一项技能，随时提问即可。

**流程 (flow)** 是穿越各项技能的执行路径。大多数工作沿一条**主流程 (main flow)** 推进，并有两个**汇入支线 (on-ramps)** 汇入其中。其余各项则为独立工具，或在底层运行的词汇规范层。

## 主流程：从构想到交付 (idea → ship)

大多数工程任务所遵循的路径。你有一个构想并希望将其构建出来。

1. **`/grill-with-docs`** — 通过深度访谈打磨构想。只要你在**有效工作目录中工作**，就从这里开始：它是带状态的，会将沉淀的认知保留在 `CONTEXT.md` 和 ADR 中。（没有工作目录？使用 `/grill-me` — 参见独立工具。两者底层运行相同的 `/grilling` 原语；`grill-with-docs` 会留下文档足迹，因此只要存在仓库供其记录，它就是两者中更优的选择。）
2. **分支判定 — 能否在对话中解决所有疑问？** 若某个问题需要可运行的答案（状态、业务逻辑、必须亲眼见到的 UI），则绕道进行原型构建，两端均通过 **`/handoff`** 衔接（原型位于独立目录中，这正是 `/handoff` 的适用场景 — 参见阶段边界）：
   - 执行 **`/handoff`** 导出上下文，随后针对该文件开启全新会话，
   - 运行 **`/prototype`** 使用一次性代码回答该问题，
   - 将所获成果通过 **`/handoff`** 带回，并在原始构想对话中对其进行引用。
3. **分支判定 — 这是否属于跨多会话的大型构建？**
   - **是** → 执行 **`/to-spec`**（将对话转化为规格说明），随后执行 **`/to-tickets`** 将其拆解为示踪弹 Ticket（Tracer-bullet tickets），每个 Ticket 明确声明其**阻塞依赖边 (blocking edges)**。在本地追踪系统中，表现为 `.scratch/<feature>/issues/` 下每个 Ticket 对应一个独立文件，按阻塞依赖由浅入深手动推进；在真实追踪系统中，依赖边转为原生阻塞关联，从而可以随时认领已解除阻塞的 Ticket——针对每个 Ticket 启动 **`/implement`**，并在**每个 Ticket 之间使用 `/clear` 清空上下文**。每个 Ticket 都是自包含的，因此上一个 Ticket 的会话上下文完全可以废弃。
   - **否** → 直接在当前相同的上下文窗口中运行 **`/implement`**。

   无论哪种方式，**`/implement`** 都会在内部驱动 **`/tdd`** 来构建每个 Issue（一次推进一个红-绿切片），并在 Commit 之前运行 **`/code-review`** 进行针对 Diff 的双维度审查（规范 + 规格）以收尾。当你只想以测试优先方式构建具体行为而不需要完整规格时，可单独使用 **`/tdd`**；当你希望针对固定基准点审查分支或 PR 时，可单独使用 **`/code-review`**。

### 上下文整洁度规范 (Context hygiene)

将步骤 1–3 保持在**单个连续的上下文窗口**中——在 `/to-tickets` 执行完成之前切勿执行压缩（compact）或清空（clear）——以便盘问、规格说明和 Ticket 全部建立在同一套思考基石之上。随后每个 `/implement` 从各自的 Ticket 出发，开启全新的干净上下文。

此操作的上限在于**[聪明区 (smart zone)](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**：即模型依然能够敏锐严谨推理的有效窗口容量（在当今顶尖模型上约为 15 万 Token）。若会话在到达 `/to-tickets` 之前接近该上限，切勿勉强在退化状态下继续推进——在最近的阶段边界处执行 `/compact`，然后继续进行（参见阶段边界）。

## 汇入支线 (On-ramps)

产生工作任务并最终汇入主流程的起始情境。

- **Bug 和需求不断堆积** → **`/triage`**。它推动 Issue 穿越分类定级角色，产出 Agent 就绪的 Issue，供随后的 **`/implement`** 认领。

  分类定级仅适用于**非你自己创建**的 Issue——Bug 报告、收到的新需求、任何以原始形态到来的内容。由 `/to-tickets` 生成的 Ticket 本身就已经是 Agent 就绪的，因此**不要对其进行二次 triage**。

- **系统出现故障** → **`/diagnosing-bugs`**。适用于疑难杂症：初看难以捉摸的 Bug、偶发的不稳定问题（Flake）、在两个已知良好状态之间悄然引入的回归。在建立**紧凑反馈循环**（即一条能够在此 Bug 上稳定飘红的单行命令）之前，它拒绝空谈理论；随后通过回归测试予以修复。当复盘发现根本原因在于代码库缺乏良好的缝隙（Seam）来进行故障锁定时，它会交接给 **`/improve-codebase-architecture`**。

- **庞大而迷茫的任务——全新项目或大型功能构建，远超单会话容量** → **`/wayfinder`**，这里认知要求最高的流程。当从当前位置到目标的路径尚不可见时，它会在 Issue 追踪系统上绘制一张由**决策 Ticket** 组成的**共享地图**，并逐一解决它们——产出的是**决策，而非交付物**——直至迷雾散去、道路清晰。**`/grill-with-docs`** 适合在单个会话中打磨一个构想，而 wayfinder 则用于你无法一屏容纳的宏大构想——它更为从容和严密，因此请严格用于此类场景，绝不要用于边界明确的功能。

  当决策地图完全清晰后，**它负责交接，而不直接构建**：在 **`/to-spec`** 处汇入主流程，将地图中相互关联的决策浓缩为可构建的计划，随后照常执行 `/to-tickets` 和 `/implement`。将地图直接接入 `/implement` 会跳过这种浓缩过程并丢失关联细节——只有当任务最终被证明确实极小微不足道时，才直接进入 `/implement`。

## 代码库健康治理 (Codebase health)

非新功能开发——属于日常维护。

- **`/improve-codebase-architecture`** — 随时利用空闲时间运行，以确保代码库始终适合 Agent 高效开展工作。它能发现**模块深化机会 (deepening opportunities)**；挑选其中一个机会将*产生一个构想*，你可以将其带入主流程的 `/grill-with-docs` 中。它是发现候选机会的侦察兵；而下文的 **`/codebase-design`** 则是你针对选定方案进行架构设计的工作台。

## 底层词汇体系 (Vocabulary underneath)

在其他技能*底层*运行的两个模型触发参考规范——各自为其领域的词汇体系提供单一事实来源。当问题出在**概念术语**而非执行流程时，可直接查阅它们；或由上述技能按需引入。

- **`/domain-modeling`** — 提炼项目的*业务领域*语言：推敲模糊术语、化解一词多义（如“账户/account”同时承担三项职责）、将难以逆转的决策沉淀为 ADR。它是 `/grill-with-docs` 在内部驱动的实践规范，旨在保持 `CONTEXT.md` 为一份干净精准的术语表。
- **`/codebase-design`** — 深模块词汇体系（模块 module、接口 interface、深度 depth、缝隙 seam、适配器 adapter、杠杆率 leverage、局部性 locality），用于设计模块的*形态*：在清晰的缝隙处，通过狭小的接口承载丰富深厚的行为。`/tdd` 和 `/improve-codebase-architecture` 均以该语言为基础。

## 阶段边界 (Phase boundaries)

**阶段 (phase)** 是会话内部的一段工作——盘问、实现、QA。在两个阶段之间的**边界 (boundary)** 处，你有五种选择，而在这五者之间做出抉择是整张地图中最需要权衡判断的决策：

- **继续 (Continue)** — 留在当前会话。无任何开销，无信息损失。
- **`/clear`** — 清空上下文窗口，当之前的所有内容与后续工作无关时使用。
- **`/handoff`** — 编写可移植的 Markdown 文件。场景严格受限：仅用于**切换新工具环境**、**切换新目录**、**移交同事**、或在**阶段进行中**分叉出旁支任务。其买到的是**可移植性**。
- **子 Agent (Subagent)** — 将边界清晰的任务派发到其独立的上下文中运行并收回报告。
- **`/compact`** — 压缩当前上下文，并用其总结作为全新会话的种子。这是**兜底选项**，位于决策树底部而非首选。

阅读 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md) 了解有序决策树——五个判断问题、每个分支背后的权衡逻辑，以及为何一手来源成本使得**继续 (Continue)** 成为最先应当考虑的选项。请务必**在**阶段边界处做决策；在阶段进行中，要么继续，要么将剩余部分拆分为子 Agent。

## 独立工具 (Standalone)

完全脱离主流程的独立技能。

- **`/grill-me`** — 与 `/grill-with-docs` 相同的深度盘问，但为**无状态**：不在本地保存任何文件，也不构建 `CONTEXT.md`。当你**不在有效工作目录中工作**时使用——打磨计划、设计、文案、任何没有依托代码仓库的内容。若你在工作目录中，请使用 `/grill-with-docs`：它运行完全相同的盘问，同时会留下文档足迹，因而是绝对更优的选择。
- **`/grilling`** — 盘问机制本身的原语：轮次、前沿边界、事实是 Agent 的职责、决策属于用户。`/grill-me` 和 `/grill-with-docs` 是两种具名的入口，而 `/triage`、`/wayfinder` 和 `/improve-codebase-architecture` 均在内部运行它。仅当你需要没有任何包装的原语盘问时才直接调用。
- **`/resolving-merge-conflicts`** — 逐块处理正在进行的 merge 或 rebase 冲突，通过追溯双方一手来源中的**意图**来化解冲突，而非盲目挑选代码行，进而完成操作。它绝不会执行 `--abort`。完全独立于所有常规流程：在已经处于冲突中时调阅。
- **`/prototype`** — 构建小型一次性抛弃型程序以解答某个设计疑问：这种状态模型是否合理，或者 UI 应该呈现为何种形态。“抛弃型”是对代码编写方式的约束，而非必须将其销毁的承诺：其沉淀的结论融入正式代码中，而原型本身作为**一手来源**保留在脱离 main 的 `prototype/<name>` 分支上，并在实现的 Issue 中予以引用。它是主流程步骤 2 的绕道工具，但在任何难以在纸面上达成定论的设计疑问出现时，均可随时使用。
- **`/research`** — 将阅读调研的繁重工作委派给**后台 Agent**：它针对**一手来源**开展问题调研，随后在仓库中生成一份附带详尽引用的 Markdown 文件。在它阅读调研的同时，你可以继续自己的工作。它产出的文件可以带入主流程的 `/grill-with-docs` 中——调研是为思考提供养分，而非取代思考。
- **`/to-questionnaire`** — 当阻碍你的关键信息既不在你的脑海中也不在代码库中，而是在**其他人的脑海中**时，生成一份供其填写的问卷。它是 `/grill-me` 的逆向操作：不对你进行专业主题的盘问，而是针对**发送背景**对你进行访谈（发送给谁、你需要得到什么），并将问题直指认知差距。收回的答案是 `/grill-with-docs` 或 `/to-spec` 的绝佳素材。
- **`/wizard`** — 专用于只有**人类**才能完成的步骤：配置基础设施、设置凭据或 CI 密钥、在陌生的第三方控制台中点击操作、执行一次性迁移或上线切换。它生成交互式 Bash 脚本，自动打开每个 URL、捕获每个配置值并写入 `.env` 和 GitHub Secrets——从而使这些流程不再需要每次都向 Agent 重新解释一遍。属于模型触发技能，当 Agent 撞上唯有人类才能跨越的墙壁时便会主动调阅。若 Agent 自身有能力直接完成，它应当直接执行；这仅适用于确实需要人类介入闭环的场景。
- **`/wait-what`** — 用于纠正未被理解的消息。在对话进行中、任何其他技能内部随时调用，Agent 会结合你所缺失的上下文，以浅显通俗的语言并运用 `CONTEXT.md` 中的词汇重新阐述刚才的内容。它属于事后补救；而 `/grill-with-docs` 是事前预防，因为早期约定的统一语言能够从源头上避免晦涩术语的出现。
- **`/teach`** — 跨多个会话学习某个概念，将当前目录作为带状态的教学工作区。
- **`/writing-for-agents`** — 编写 Agent 所读取文档的参考规范：涵盖 Skill、AGENTS.md、指针引用的文档等。

## 前置依赖 (Precondition)

**`/setup-matt-pocock-skills`** — 在开启第一个工程流程前运行，用于配置其他技能所依赖的 Issue 追踪系统、分类标签及文档布局。亦支持自定义 Issue 追踪系统。
