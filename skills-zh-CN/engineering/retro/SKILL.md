用户要求进行一次**复盘 (retrospective)**。你的任务是为编码 Agent 的**环境**提出改进建议，提升后续运行的效果。

## 执行步骤

1. 调用 Skill 工具，传入 `writing-for-agents`，获取写作风格规范。

2. 阅读用户指定会话的一手来源。这可能需要搜索本机上的会话日志。若用户未指定会话，默认复盘当前会话。

3. 从以下类别中寻找改进候选项。

- **导航 (Navigation)**：Agent 找到正确文件是否容易？文件之间是否存在隐藏依赖？加入**导航指针 (navigation pointer)** 是否有帮助？*适用情形*：会话中为寻找某条信息花费了很长时间。
- **自动化检查 (Automated checks)**：是否存在可以捕获 Agent 所犯错误的自动化检查？例如 Lint、类型检查、测试或文件系统检查。先阅读仓库自己的检查命令，包括 `package.json` 或构建工具中的 `lint`、`check` 脚本及 CI 工作流。如果检查已存在但未接入流程，或已悄然失效，应将其作为发现的问题，而非重新实现。仓库若没有任何**防护机制 (guardrail)**，即既没有 pre-commit 钩子，也没有运行 Lint、类型检查或测试命令的 CI 任务，这本身就是一个问题：没有 Lint 防护是持续错失的检查机会，并非无关紧要的默认状态。*适用情形*：Agent 犯了本可通过自动化检查捕获的错误，或仓库完全缺少防护机制。
- **编码规范 (Coding standards)**：是否应为**审查 Agent (reviewer agent)** 增加一条需要执行的规则？是否应删除或澄清既有规则？先判断违规的性质：**机械性**违规，例如固定语法模式、禁止使用的 API、导入形式或文件位置规则，必须使用确定性检查。根据仓库语言及已有防护机制，选择成本最低的方式：在仓库现有 Linter 中增加自定义规则、新增 pre-commit 钩子，或新增 CI 任务。默认实现检查，而非写下规则。`CODING_STANDARDS.md` 仅保留真正需要**判断 (judgement calls)** 的事项，例如跨文件一致性、“符合周边风格”，以及防护机制无法替代的判断。*适用情形*：审查 Agent 未能发现某个错误。
- **全局 AGENTS.md**：是否有引导指令应改为编码规范或自动化检查？*适用情形*：仓库内或用户全局范围内的 AGENTS.md 特别庞大。
- **工具调用成本 (Tool economy)**：Agent 是否进行了可精简的高成本工具调用？是否有自定义工具，例如 CLI 或 MCP，在 Token 消耗上特别低效？*适用情形*：Agent 进行过高成本工具调用。
- **无效指令 (No-ops)**：寻找引导文件中不会改变 Agent 行为的指令。*适用情形*：引导文件庞大且难以维护。
- **信息访问 (Information access)**：寻找增加 Agent 信息访问能力的机会，例如将开发服务器日志同时输出到可读取的位置，或授予第三方服务的只读访问权限。*适用情形*：Agent 无法获得某条关键信息。

4. 按严重程度排序，向用户呈现这些候选项。

## 参考

### 实现与审查 (Implementation vs Review)

所有工作都经过实现和审查两个阶段。实现 Agent 的**上下文压力 (context pressure)** 最大，需要负责探索、编写代码和排查失败。

审查 Agent 的上下文压力最小：它直接收到 Diff，无需探索，通常也不需要编写代码或调试。

因此，应由审查 Agent 负责落实编码规范，而非实现 Agent。

### 文件

你可以使用仓库中的以下文件：

- `CLAUDE.md` / `AGENTS.md`：这些文件会被放入在本仓库工作的每个 Agent 的上下文窗口中，应极其克制地使用，通常仅放置通向其他文件的**导航指针**。
- `CODING_STANDARDS.md`：该文件在审查阶段读取，而非实现阶段。若规范超过 1,000 行，则增加指向文档目录的**导航指针**。
- 文档：作为由其他文件指向的参考资料。创建新文档前，先查找已有文档。
- 技能：用于提供文档，因为其描述会进入 Agent 的上下文窗口，或用于承载用户触发的命令。遵循 `writing-for-agents` 技能中的建议。
