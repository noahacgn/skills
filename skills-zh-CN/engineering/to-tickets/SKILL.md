# 拆解为 Ticket (To Tickets)

将计划、Spec 或对话拆解为一组 **Ticket**——每个 Ticket 都是一条垂直切片的示踪弹（Tracer bullet），并显式声明哪些 Ticket 对其构成**阻塞 (block)**。

Issue 追踪系统与分类标签词汇表应已配置完毕——若未配置，请运行 `/setup-matt-pocock-skills`。

## 执行流程

### 1. 收集上下文

从当前对话上下文中提取信息。若用户作为参数传入了引用（Spec 文件路径、Issue 编号或 URL），获取该引用并通读其完整正文与评论。

### 2. 探索代码库（可选）

若尚未探索代码库，进行勘察以了解当前代码状态。Ticket 的标题与描述应严格使用项目的业务领域术语，并遵循所涉及区域的 ADR。

寻找对代码进行**预重构 (Prefactor)** 的机会以降低实现阻力。“先让变更变容易，再做容易的变更。”

### 3. 起草垂直切片

将工作拆分为**示踪弹 (tracer bullet)** 类型的 Ticket。

<vertical-slice-rules>

- 每个切片垂直贯穿所有层级（Schema、API、UI、测试），切出狭窄但完整的闭环路径——必须是垂直切片，坚决杜绝单层的水平切片
- 完成的单个切片自身必须是可独立演示或可独立验证的
- 每个切片的大小必须恰好能够装入单个干净的上下文窗口中
- 任何预重构工作应当优先作为前置切片完成

</vertical-slice-rules>

为每个 Ticket 赋予明确的**阻塞依赖边 (blocking edges)**——即在当前 Ticket 启动前必须先完成的其他 Ticket。没有前置阻塞项的 Ticket 可以立即开工。

**大范围重构是垂直切片的例外场景。** **大范围重构 (wide refactor)** 是指单一机械化变更（如重命名列、重构通用类型符号），其**爆炸半径 (blast radius)** 席卷整个代码库，单次修改会同时破坏数千个调用点，因而无法形成任何单独绿灯的垂直切片。切勿强行将其塞入单颗示踪弹；应按**扩展–收缩 (expand–contract)** 模式进行编排。首先扩展：在旧结构旁添加新结构，确保现有系统完全不破损。随后按爆炸半径分批迁移调用点（按代码包、按目录分批），每批作为一个独立的 Ticket 并被扩展步骤阻塞；由于旧结构依然存在，CI 能够在批次之间持续保持绿灯。最后收缩：当所有调用点迁移完毕后，在被所有迁移批次阻塞的收尾 Ticket 中彻底删除旧结构。当即使分批也无法独立保持绿灯时，保持该顺序但让它们共享一个集成分支，共同阻塞最终的集成与验证 Ticket——只在最后一步保证绿灯。

### 4. 与用户对齐确认

将拟定的拆解清单以编号列表形式呈现。对每个 Ticket 展示：

- **标题 (Title)**：简短描述性名称
- **前置阻塞项 (Blocked by)**：必须先完成哪些其他 Ticket（若有）
- **交付内容 (What it delivers)**：该 Ticket 贯通实现的端到端行为

向用户询问：

- 粒度是否合适？（太粗 / 太细）
- 阻塞依赖边是否正确——每个 Ticket 是否仅依赖真正卡点的前置 Ticket？
- 是否有任何 Ticket 需要进一步合并或拆分？

持续迭代直至用户批准拆解方案。

### 5. 将 Ticket 发布到配置的追踪系统中

发布已批准的 Ticket。**具体发布方式**取决于 `/setup-matt-pocock-skills` 所配置的追踪系统——无论哪种方式，Ticket 内容本身完全一致，仅阻塞依赖边的形态有所不同：

- **本地文件** → 在 `.scratch/<feature-slug>/issues/<NN>-<slug>.md` 下以单文件管理单 Ticket，按依赖先后顺序从 `01` 开始连续编号（被依赖的阻塞项排在前面）。每个文件的“Blocked by”列出其依赖的编号/标题。使用下方的单 Ticket 文件模板——单文件单 Ticket，绝不要合成为单个大文件。
- **真实 Issue 追踪系统 (GitHub, Linear 等)** → 按依赖顺序逐个发布 Issue（前置阻塞项先发布），以便后续 Ticket 的阻塞边能够引用真实的实体 ID。在平台支持原生阻塞 / Sub-issue 关联时优先采用原生关联；否则将每个 Ticket 的“Blocked by”指向对应的阻塞 Issue。除非另有指示，统一打上 `ready-for-agent` 标签——这些 Ticket 在构造上天然支持 Agent 独立认领。

始终关注并推进**前沿边界 (frontier)**：即所有前置阻塞项均已完成的任何 Ticket。对于纯线性依赖链，这意味着自顶向下依序推进。

**切勿**关闭或修改任何父级 Issue。
