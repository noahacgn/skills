# 改进代码库架构 (Improve Codebase Architecture)

暴露架构摩擦并提议**模块深化机会 (deepening opportunities)**——将浅模块重构为深模块。其目标是增强代码的可测试性以及对 AI 导航的友好度。

本命令*依托*项目的业务领域模型，并建立在通用的设计词汇体系之上：

- 调用 Skill 工具并传入 `"codebase-design"`，以获取架构词汇（**模块 module**、**接口 interface**、**深度 depth**、**缝隙 seam**、**适配器 adapter**、**杠杆率 leverage**、**局部性 locality**）及其核心原则（删除测试法、“接口即测试暴露面”、“单适配器 = 假想缝隙，双适配器 = 真实缝隙”）。在每条建议中严格使用这些术语——切勿混淆使用“组件 (component)”、“服务 (service)”、“API”或“边界 (boundary)”。
- `CONTEXT.md` 中的业务领域语言为良好的缝隙赋予清晰的业务名称；`docs/adr/` 中的 ADR 记录了已有决策，本命令不应重复讨论已定论的决策。

## 执行流程

### 1. 探索与扫描 (Explore)

**在扫描前明确范围——遵循 YAGNI 原则。** 深化一个模块的回报在于让未来的变更更加从容，因此应重点关注代码库中近期频繁变动的区域。在开始查看代码前先确定*看哪里*：

- 若用户指定了明确方向——某个模块、子系统或痛点——直接采纳，跳过下方的自动推断。
- 否则，回溯一段 Git Commit 历史（`git log --oneline`）寻找代码库的热点（Hot spots）——即反复出现的文件和区域——让这些路径优先吸引你的注意力。若变更极为分散且无明显热点，再适度扩大搜索范围。

首先阅读项目的业务领域术语表（`CONTEXT.md`）以及所涉及区域内的任何 ADR。

随后派发子 Agent 遍历代码库。不要机械遵循教条式的启发规则——进行有机探索，并记录你在何处感受到了架构摩擦：

- 在何处理解单个业务概念需要穿梭于大量细碎的浅模块之间？
- 哪些模块属于**浅模块**——接口的复杂度几乎与内部实现持平？
- 哪些地方为了单纯追求可测试性而强行提炼了纯函数，但真正的 Bug 却隐藏在其混乱的调用方式中（缺乏**局部性**）？
- 哪些紧耦合的模块在其缝隙处发生了抽象泄漏？
- 代码库的哪些部分缺乏测试，或很难通过其现有接口进行测试？

对任何你怀疑属于浅模块的实体应用**删除测试法**：删除它会使复杂度高度集中，还是仅仅把复杂度搬移到了别处？如果答案是“会集中起来”，这就是你正在寻找的信号。

### 2. 以 HTML 报告呈现候选方案 (Present candidates as an HTML report)

在操作系统的临时目录下编写一个自包含的单文件 HTML 报告，确保不向代码仓库中写入垃圾文件。临时目录优先从 `$TMPDIR` 获取，兜底回退到 `/tmp`（在 Windows 上为 `%TEMP%`），写入路径为 `<tmpdir>/architecture-review-<timestamp>.html`，确保每次运行生成全新文件。为用户自动打开该文件——在 Linux 上执行 `xdg-open <path>`，在 macOS 上执行 `open <path>`，在 Windows 上执行 `start <path>`——并告知用户其绝对路径。

报告使用 **CDN 引入的 Tailwind** 负责布局与样式，使用 **CDN 引入的 Mermaid** 绘制能够清晰传达结构的关系图/流程图/时序图。将 Mermaid 与手写的 CSS/SVG 视觉图表相结合——当关系呈图结构（调用图、依赖图、时序图）时使用 Mermaid；当需要更具信息表现力的视觉呈现（体量图、剖面图、折叠收敛动画）时使用手写的 div/SVG。为每个候选方案提供**改造前/改造后对比可视化 (before/after visualisation)**。保持高水准的视觉化。

为每个候选方案渲染一张卡片，包含：

- **涉及文件 (Files)** — 涉及哪些文件/模块
- **当前问题 (Problem)** — 为什么现有架构会引发开发摩擦
- **解决方案 (Solution)** — 用浅显通俗的语言描述将发生什么改变
- **预期收益 (Benefits)** — 用局部性和杠杆率的术语阐述收益，以及测试将如何得到改善
- **改造前/后架构图 (Before / After diagram)** — 左右并排、定制绘制，直观展现浅模块消除与深化过程
- **推荐力度 (Recommendation strength)** — `强烈推荐 (Strong)`、`值得探索 (Worth exploring)`、`前瞻设想 (Speculative)` 之一，以徽章形式渲染

报告以**首要推荐 (Top recommendation)** 小节收尾：说明你建议优先着手哪一个候选方案及其理由。

**领域概念严格使用 CONTEXT.md 词汇，架构设计严格使用 `/codebase-design` 词汇。** 若 `CONTEXT.md` 定义了“Order”，请表述为“Order 受理模块 (Order intake module)”——而非“FooBarHandler”，也不是“Order 服务”。

**ADR 冲突处理**：若候选方案与现有 ADR 冲突，仅当架构摩擦确实严重到值得重新审视该 ADR 时才提出。在卡片中清晰标记（例如带有警示框：*“与 ADR-0007 存在冲突——但值得重新讨论，因为……”*）。不要罗列 ADR 明令禁止的纯理论性重构。

完整 HTML 脚手架、图表模式与样式指南参见 [HTML-REPORT.md](HTML-REPORT.md)。

在此阶段**切勿**提前构想具体接口。文件写入完成后，询问用户：“你希望深入探索哪一个方案？”

### 3. 盘问闭环 (Grilling loop)

一旦用户选定候选方案，调用 Skill 工具并传入 `"grilling"`，与用户一起梳理决策树——约束条件、依赖关系、深化后模块的形态、缝隙背后的内容、哪些测试得以保留。

随着决策逐渐成型，就地执行连带操作——调用 Skill 工具并传入 `"domain-modeling"`，保持业务领域模型实时同步：

- **以尚未收录在 `CONTEXT.md` 中的概念命名深化后的模块？** 将该术语添加到 `CONTEXT.md`。若文件不存在则按需创建。
- **在对话中澄清了某个模糊术语？** 立即就地更新 `CONTEXT.md`。
- **用户以具有实质性权衡的理由拒绝了候选方案？** 提议编写 ADR，引导方式如：*“需要我将其记录为 ADR，以便未来的架构审查不再重复提议吗？”* 仅当该理由确实需要被未来的探索者知晓以避免重复走弯路时才提议——跳过临时性理由（“现在精力不够”）与显而易见的理由。
- **希望为深化后的模块探索替代接口？** 调用 Skill 工具并传入 `"codebase-design"`，运用其二度设计的并行子 Agent 模式。
