# UI 原型构建规范 (UI Prototype)

在单条路由上生成**数个截然不同的 UI 变体**，支持通过屏幕底部的悬浮工具栏自由切换。用户在浏览器中穿梭对比各个变体，挑选出最中意的一个（或博采众长融合各变体的亮点），随后将其余抛弃。

若问题涉及逻辑或状态流转而非视觉形态——请切换到 [LOGIC.md](LOGIC.md)。

## 适用场景

- “这个页面应该设计成什么样？”
- “在正式编码前，我想先看几个不同风格的 Dashboard 选项。”
- “为设置页面尝试几种不同的布局方案。”
- 任何原本需要花费一整天在脑海中纠结几个模糊草图的场景。

## 两种形态——强烈推荐形态 A

当 UI 原型**直接嵌入现有应用的真实上下文**（真实 Header、真实侧边栏、真实数据密度）中时，其评估效果远胜于孤立存在。脱离宿主环境的一次性独立路由处于信息真空：每个变体在孤立状态下看起来都还不错。只要存在能够承载这些变体的既有页面，默认采用形态 A。仅当原型确实找不到就近载体时才采用形态 B。

### 形态 A — 在既有页面上调整（首选）

路由已存在。多个变体渲染在**同一条路由**上，通过 `?variant=` URL 查询参数进行切换。原有的数据获取、参数和鉴权逻辑全部保留——仅仅切换渲染子树。这是默认推荐方式；除非有特殊理由，一律首选此形态。

若原型针对的是尚未拥有独立页面、但*天然应位于某个既有页面内部*的功能（例如 Dashboard 的新区块、设置页面的新卡片、已有流程中的新步骤）——同样属于形态 A。将变体挂载在宿主页面内部即可。

### 形态 B — 新增独立页面（兜底方案）

仅当被原型的功能确实没有任何既有页面可以承载时使用——例如一个全新的顶层业务入口，或无法嵌入任何合理位置的全新独立流程。

遵循项目既有的路由约定创建**一次性路由**——切勿自行发明新的顶层目录结构。命名保持原型标识（例如在路径或文件名中包含 `prototype`）。同样采用 `?variant=` 模式。

在决定采用形态 B 之前，请严格自省：真的没有现成页面可以嵌入吗？空荡荡的孤立路由往往会掩盖那些在内容充实时才会暴露的设计缺陷。

在两种形态中，底部的悬浮切换条完全通用。

## 执行流程

### 1. 明确核心疑问并设定变体数量 N

默认提供 **3 个变体**。超过 5 个将失去截然不同的设计辨识度并退化为视觉噪音——将上限控制在 5 个以内。

在原型所在位置或文件顶部用单行明确记录计划：

> “针对设置页面的三种变体，在现有 `/settings` 路由上通过 `?variant=` 支持动态切换。”

### 2. 生成截然不同的变体

起草每个变体。每个变体必须满足：

- 紧密契合页面的核心业务目的及其能够获取的数据。
- 遵循项目自身的组件库 / 样式系统（TailwindCSS、shadcn、MUI、原生 CSS 等）。
- 具备清晰的导出组件命名，例如 `VariantA`、`VariantB`、`VariantC`。

变体之间必须存在**结构性差异 (structurally different)**——不同的布局骨架、不同的信息层级、不同的首要交互入口，而绝非仅仅更换背景颜色。三个微调了边距的卡片网格不算 UI 原型，那只是壁纸换肤。若两个初稿过于雷同，以“禁止使用卡片网格”等明确约束重构其中一个。

### 3. 将变体组合连接

在路由页面中创建一个简单的切换器组件：

```tsx
// 伪代码 — 根据项目具体框架灵活调整
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

对于形态 A（既有页面）：将所有数据获取逻辑保留在切换器之上；仅随变体切换下游渲染子树。

对于形态 B（新页面）：在 `/prototype/<name>` 下的一次性路由上挂载相同的切换器。

### 4. 构建悬浮切换工具栏 (Floating Switcher)

位于屏幕底部中央的轻量固定定位条，包含三部分：

- **左箭头** — 切换到上一个变体（循环轮播）。
- **变体标签** — 显示当前变体标识符及具名描述（若有），如 `B — 侧边栏布局`。
- **右箭头** — 切换到下一个变体（循环轮播）。

交互行为规范：

- 点击箭头更新 URL 查询参数（使用框架自带的 Router — Next.js 使用 `router.replace`，React Router 使用 `navigate` 等），确保变体支持 URL 共享并在刷新后状态保持。
- 键盘快捷键：`←` 和 `→` 方向键同样支持切换。当 `<input>`、`<textarea>` 或 `[contenteditable]` 处于聚焦状态时，切勿拦截方向键。
- 视觉与页面有明显区隔（例如高对比度胶囊药丸样式、柔和阴影），使其明显区别于正在评估的页面内容。
- 在生产构建中自动隐藏——通过 `process.env.NODE_ENV !== 'production'` 或类似检查进行拦截，防止原型代码意外合并后流向终端用户。

将切换器封装为单个通用组件，便于形态 A 与形态 B 复用。

### 5. 交付评估

交付 URL（及各个 `?variant=` 参数）。用户在有空时会逐一浏览对比。最宝贵的反馈通常是：**“我想要 B 的头部配合 C 的侧边栏”**——这正是最终的最佳方案。

### 6. 沉淀结论并清理归档

一旦某个变体胜出，记录结论——选定了哪个变体及背后理由——随后按照 [SKILL.md](SKILL.md) 规范进行沉淀。将胜出方案融入正式代码，将其余内容移至一次性分支，而非合并入 main：

- **形态 A** — 将胜出变体融入现有页面；从 main 中删除落选变体及切换器组件。
- **形态 B** — 将胜出变体晋升为正式路由；从 main 中删除一次性原型路由及切换器。

整套变体作为一手来源保留在独立的一次性分支上，切勿直接丢弃——但若留在主分支中会迅速腐化并误导后续开发者。

## 反模式警示

- **变体之间仅有颜色或文案差异。** 那叫微调，不叫原型。真正的变体在结构上存在分歧。
- **变体间过度共享代码。** 共享 `<Header>` 是合理的；但若强行共享 `<Layout>` 则会扼杀变体的多样性。每个变体都应当有权自由颠覆布局。
- **将变体连接到真实的数据变更（Mutation）。** 只读原型即可满足诉求。若变体涉及修改操作，对接 Stub 假数据——此处解答的是“应该长什么样”，而非“后端逻辑是否打通”。
- **将原型代码直接晋升为生产代码。** 变体代码是在原型约束下编写的（无测试、极简错误处理）。在正式合并融入时应当进行规范重写。
