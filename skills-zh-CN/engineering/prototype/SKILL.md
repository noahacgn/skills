# 原型构建 (Prototype)

原型是**用于解答特定疑问的一次性抛弃型代码**。疑问的性质决定了原型的具体形态。

## 选择分支方向

从用户的提示词、周边代码或直接向在席的用户询问，以明确正在回答哪类问题：

- **“这套业务逻辑 / 状态模型是否合理？”** → [LOGIC.md](LOGIC.md)。构建单个可共享的 HTML 文件——包含自由探索按钮与分标签的引导式演练——让状态机穿越在纸面上难以推导的复杂边界用例，且支持非技术人员独立操作。
- **“界面视觉与交互应当做成什么样？”** → [UI.md](UI.md)。在单条路由上生成数个截然不同的 UI 变体，通过 URL 查询参数和底部悬浮工具栏支持自由切换。

这两个分支产出完全不同的产物——选错分支会导致整个原型白费。若问题本身具有歧义且无法立即联系到用户，默认选择与周边代码更契合的分支（后端模块 → 逻辑分支；页面或组件 → UI 分支），并在原型顶部明确注明该假设。

## 两分支通用的基本法则

1. **从第一天起就定位为一次性代码，并予以明确标记。** 将原型代码放置在它实际将被使用的就近位置（紧邻它所模拟的模块或页面），以保证上下文一目了然——但对其命名必须清晰，让任何读者都能一眼识别出这是原型而非生产代码。对于一次性 UI 路由，遵循项目已有的路由约定，不要另造顶层结构。
2. **启动运行极简。** UI 原型通过项目任务运行器中的单条命令即可启动——`pnpm <name>`、`python <path>`、`bun <path>` 等。逻辑演示原型是一个双击即可直接打开的单文件 HTML。无论哪种方式，启动均无需任何思考门槛。
3. **默认无需持久化。** 状态驻留在内存中。持久化是原型正在*检验*的内容，而非原型应该依赖的前提。若问题明确涉及数据库，连接临时草稿数据库或使用带有醒目“PROTOTYPE — wipe me”命名的本地文件。
4. **拒绝过度打磨。** 不写测试，不写超出让原型*正常运行*所必需的错误处理，不做过度抽象。核心目的在于快速沉淀认知。
5. **显式呈现内部状态。** 每次操作后（逻辑分支）或每次切换变体时（UI 分支），打印或渲染出完整的关键状态，让用户能够亲眼观察到变化。
6. **完成后妥善沉淀。** 将验证通过的决策沉淀到正式代码中，随后将原型本身作为**一手来源**保留：将其提交到脱离 main 分支的一次性独立分支上，并在具体实现的 Issue 中留下指向该分支的上下文指针。同时在 Issue 或 Commit 中记录结论——验证结果及据此拍板的疑问。主分支仅保留经过验证的最终决策。
