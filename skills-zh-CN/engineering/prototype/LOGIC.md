# 逻辑原型构建规范 (Logic Prototype)

单个自包含的 HTML 文件——一份**可共享的交互演示**——让任何人都能通过点击按钮来驱动状态模型。当问题涉及**业务逻辑、状态流转或数据形态**时选用——即那些在纸面上看似合理，但只有在亲历真实用例时才能发现别扭的事物。

由于它是一个零安装成本的单文件，你可以直接交付给非开发人员（设计师、PM、领域专家），让他们亲自体会模型运转。因此，它的界面语言应当遵循业务领域语言，而非代码术语。

## 适用场景

- “我不确定这个状态机能否处理先发生 X 接着发生 Y 的边界极端情况。”
- “这个数据模型是否真正支持表示……的场景？”
- “在落笔编码前，我想先直观感受一下这个 API 的交互形态。”
- 任何需要**点击按钮并观察状态流转**的场景。

若问题是“这个界面应该长什么样”——请切换到 [UI.md](UI.md)。

## 执行流程

### 1. 明确要回答的核心疑问 (State the question)

在编码之前，写下你正在验证的状态模型和核心疑问。在演示页面顶部用一个段落明确呈现（作为醒目的介绍文本，而非仅仅是代码注释）。解答了错误问题的逻辑原型完全是无谓浪费——将问题明确化以便后续查验，无论用户当前在线还是离线。

### 2. 将核心逻辑隔离在可移植模块中

将实际承载核心逻辑的部分（即负责解答疑问的关键逻辑）放在单个 `<script>` 块中，编写为一个纯净的独立轻量模块，后续可以直接无缝移植到正式代码库中。围绕它的外部页面是一次性的，但这个核心逻辑模块不是。

根据问题特征选择形态：

- **纯 Reducer 函数** — `(state, action) => state`。适用于离散事件驱动且状态为单一值的场景。
- **显式状态机 (State Machine)** — 明确的状态与跃迁规则。当“当前状态下哪些动作是合法的”属于核心疑问时非常适合。
- **纯函数集合** — 针对纯数据结构操作的一组纯函数。适用于无隐式上下文状态的纯数据转换场景。
- **具有清晰方法暴露面的类或模块** — 当逻辑天然需要持有运行期内部状态时使用。

选择最契合业务疑问的形态，*而非*最容易与页面绑定的形态。保持其纯粹性：不涉及 DOM 操作、不触碰 `document`、不内嵌按钮事件处理。页面单向调用该模块；绝不发生反向依赖。这使得原型在用完后依然具备长久价值：疑问一旦解答，验证无误的 Reducer / 状态机 / 函数集即可独立提取并融入正式业务模块中。

### 3. 构建可共享的 HTML 演示文件

单文件纯 HTML/CSS/JS——无前端框架、无打包工具、无后端服务，一切内联，双击即可在浏览器中打开，即使通过邮件直接发送也能直接运行。任何人只要打开它就能立即运行。

面向非开发人员编写。所有标签均采用**业务领域语言**，而非代码符号——按钮和状态描述读起来像业务概念，而非 Reducer 代码。用浅显的语言解释当前正在发生什么。

自顶向下保持清爽的布局层级：

1. **标题与一句话说明**：介绍本演示用于探索什么（来自步骤 1 的核心疑问）。
2. **当前状态展示**：完整的关键状态，渲染为易读的面板（带有清晰字段标签，而非生硬的 JSON 原始内容），每次点击后重新渲染以便观察变化。在必要处高亮提示刚才发生了什么变更。
3. **自由探索按钮区 (Free-play buttons)**：每个动作对应一个按钮，始终可用，供任何人按任意顺序自由点击把玩。每次点击分发对应 Action 并重新渲染状态。
4. **引导式演练区 (Guided walkthroughs)**：一组**业务场景 (scenarios)**，每个场景对应一个独立 Tab。每个 Tab 包含该场景的一小段浅显说明——构造了何种情境以及需要观察什么——其下方按顺序排列该场景所需**点击的步骤按钮**。每一步都是一个真实按钮：点击执行该动作并前进到下一步。开启演练会自动重置到已知的初始状态，确保场景每次运行完全确定可复现。

挑选能够展现棘手场景的用例——常规路径、复杂的边界极端情况、尝试执行本应被禁止的非法操作——这些正是纸面上难以推理的痛点。

保持视觉美观克制：排版清晰、留白充裕、单一主色调。无花哨动画，不做过度修饰——绝不喧宾夺主干扰核心状态与按钮。

### 4. 交付体验

将文件发送给相关人员，或直接在浏览器中打开。他们可以自由点击演练场景或尝试自由探索；最值得关注的反馈时刻是当他们惊呼“等等，这种情况不应该被允许发生”或“咦，我以为 X 会呈现不同的结果”——这些正是*思路与构想层面的 Bug*，而这正是原型的核心意义所在。若他们希望增加新的动作或场景，随时扩充。原型是动态演进的。

### 5. 沉淀结论与原型归档

一旦原型完成了答疑使命，记录结论，并按照 [SKILL.md](SKILL.md) 的规范对原型进行沉淀。具体逻辑映射：验证无误的 Reducer / 状态机 / 函数集提炼融入正式业务模块中（决策被正式吸收）；HTML 交互外壳保留在一次性独立分支中作为一手来源——由于是自包含单文件，它在未来依然能够随时轻松重新运行。

## 反模式警示 (Anti-patterns)

- **切勿编写测试。** 需要测试的原型就已经不再是原型了。
- **切勿连接真实数据库。** 除非疑问本身严格聚焦于持久化机制，否则一律使用内存状态。
- **切勿过早通用化。** 坚决不做“万一我们后续需要支持 X 怎么办”的设计。原型仅用于解答眼前的一个疑问。
- **切勿将业务逻辑与页面展示混为一谈。** 若纯逻辑模块引用了 DOM、`document` 或按钮事件，它就无法被干净提取。页面应当仅仅是包裹纯逻辑模块的薄薄一层外壳。
- **切勿引入框架、打包工具或服务端。** 必须是一个接收者双击即可运行的单文件；引入 React 或本地 Dev Server 会彻底破坏“随处可共享”的初衷。
- **切勿将 HTML 外壳直接打包上生产。** 页面是专门为了人工点击把玩而优化的。背后沉淀的纯逻辑模块才是唯一值得带入生产的部分。
