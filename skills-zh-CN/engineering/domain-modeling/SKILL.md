# 领域建模 (Domain Modeling)

在设计过程中主动构建并打磨项目的领域模型。这是一项**主动**的工程实践，推敲术语、构造边界用例场景，并在术语和决策成型的那一刻立即将其记录下来。（仅仅为了查阅词汇而*阅读* `CONTEXT.md` 并不属于本技能，那是任何技能都能做到的单行习惯。本技能专用于你在改变领域模型、而非仅仅消费模型的时候。）

## 文件组织结构

大多数代码库采用单一界限上下文：

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

若根目录下存在 `CONTEXT-MAP.md`，则表明代码库包含多个界限上下文。上下文地图指明了各自的存放路径：

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← 系统级全局决策
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← 订单上下文专属决策
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

按需延迟创建文件，仅在有内容需要写入时生成。若尚无 `CONTEXT.md`，在确定第一个专业术语时创建。若尚无 `docs/adr/`，在需要记录第一篇 ADR 时创建。

## 会话期间的实践准则

### 对照术语表发起质疑

当用户使用的术语与 `CONTEXT.md` 中现有的语言规范冲突时，立即指出：“你的术语表将‘cancellation’定义为 X，但你刚才的意思似乎是 Y，究竟以哪一个为准？”

### 提炼打磨模糊语言

当用户使用模糊或一词多义的词汇时，提炼并建议精确的标准术语：“你说的是‘account’，你指的是 Customer（客户）还是 User（系统用户）？这两者在领域中是不同的概念。”

### 探讨具体场景

在讨论领域实体关系时，通过具体业务场景进行压力测试。构造能够探查极端边界用例的场景，迫使用户在概念边界上给出明确清晰的定义。

### 与代码实现交叉核对

当用户陈述某项逻辑的工作原理时，检查代码实现是否相符。若发现矛盾，主动抛出：“你的代码直接取消整个 Order，但你刚才说支持部分取消，哪种才是正确的？”

### 就地更新 CONTEXT.md

一旦某个术语达成定论，立即在此刻就地更新 `CONTEXT.md`。不要批量积攒，实时沉淀。格式规范遵循 [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md)。

`CONTEXT.md` 应当完全剥离任何代码实现细节。切勿将 `CONTEXT.md` 当作 Spec 规格书、草稿板或技术选型记录库。它是一份纯粹的业务领域术语表，仅此而已。

### 克制地提出编写 ADR

仅在同时满足以下三点时，才提议创建 ADR：

1. **难以逆转**：后续推翻改变主意的成本十分巨大
2. **脱离上下文显得反直觉**：未来的读者看到代码会心生疑惑：“他们到底为什么这样设计？”
3. **真实权衡取舍的结果**：存在真正的可选方案，且出于明确原因选定了当前方案

若三者缺少其一，跳过 ADR 的编写。格式规范遵循 [ADR-FORMAT.md](./ADR-FORMAT.md)。
