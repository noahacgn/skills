# ADR 格式规范 (ADR Format)

ADR 存放在 `docs/adr/` 下，使用连续编号：`0001-slug.md`、`0002-slug.md` 等。

延迟创建 `docs/adr/` 目录，仅在需要记录第一篇 ADR 时生成。

## 模板

```md
# {决策的简明标题}

{1-3 句话：背景是什么，我们做出了什么决定，以及为什么这么决定。}
```

仅此而已。一篇 ADR 可以仅仅是一个段落。其核心价值在于记录*做出了*某项决定以及背后的*原因*，而非机械地填充各个小节。

## 可选小节

仅在确实能带来实质价值时包含以下小节，大部分 ADR 无需使用：

- **Status** 元数据 (`proposed | accepted | deprecated | superseded by ADR-NNNN`)，当决策被重新审视或推翻时非常有用
- **Considered Options (考量过的备选方案)**：仅在被否决的备选方案值得留存以防未来重复探讨时记录
- **Consequences (后果与影响)**：仅在需要特别指出非显而易见的下游连带影响时记录

## 编号规则

扫描 `docs/adr/` 中现有的最大编号并在此基础上加一。

## 何时提议创建 ADR

必须同时满足以下三项标准：

1. **难以逆转**：后续改变主意的成本非常显著
2. **脱离上下文显得反直觉**：未来的读者在查看代码时会心生疑惑：“他们究竟为什么要这么干？”
3. **真实权衡取舍的结果**：存在真正的可选替代方案，且出于具体理由选定了当前方案

若一项决策很容易逆转，忽略它，后续直接改回去即可。若决策显而易见，没人会怀疑为什么。若不存在其他备选项，除了“我们做了理所当然的事”之外也没什么值得记录的。

### 哪些内容符合 ADR 记录标准

- **架构形态。** “我们采用 Monorepo 单体大仓模式。” “写入模型采用事件溯源 (Event Sourcing)，读取模型投影到 Postgres 中。”
- **界限上下文之间的集成模式。** “订单 (Ordering) 与计费 (Billing) 之间通过领域事件通信，而非同步 HTTP 调用。”
- **具有技术绑定的选型。** 数据库、消息中间件、认证提供方、部署目标环境。并非每个代码库依赖库都要写，仅记录那些一旦替换需要耗费数月精力的核心选型。
- **边界与职责范围决策。** “客户数据完全由 Customer 上下文归口管理；其他上下文仅通过 ID 进行引用。” 明确的“否定”与“肯定”同样具有重大价值。
- **深思熟虑后偏离常规路径的做法。** “出于 X 原因，我们采用手写 SQL 而非 ORM。” 任何合理读者可能会预先假设反向做法的场景。这能防止下一位工程师“顺手修复”本就是有意为之的设计。
- **无法在代码中直观看到的外部硬性约束。** “由于合规监管要求，我们无法使用 AWS。” “受限于合作伙伴的 API 契约，响应时间必须控制在 200ms 以内。”
- **被否决的方案（当否决原因并非浅显易懂时）。** 如果你深度评估过 GraphQL 最终出于细微权衡选择了 REST，记录下来，否则六个月后一定会有人再次提议 GraphQL。
