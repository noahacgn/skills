# 疑难故障排查诊断 (Diagnosing Bugs)

针对疑难 Bug 的严谨工程规范。仅在具备明确理由时才允许跳过特定阶段。

在探索代码库时，阅读 `CONTEXT.md`（若存在）以建立相关模块的清晰心智模型，并检查所涉及区域的 ADR。

## 敏感信息脱敏 (Redact)

本技能要求展示命令、输出以及捕获的产物。**首先对所有敏感凭据进行脱敏**——用 `<REDACTED>` 替代。基于环境变量构建闭环，让凭据保留在运行环境中，而非暴露在你的展示输出中。捕获的产物中常带有认证 Header：仅引用承载关键信号的行。

若脱敏后的输出不足以诊断 Bug，明确说明并向用户询问。

## 阶段 1 — 构建反馈循环 (Build a feedback loop)

**这是本技能的核心精髓。** 其他一切都是机械化流程。若你手头拥有一个针对该 Bug 的**紧凑**通过/失败信号——一个能够在此 Bug 上稳定飘红的信号——你终将找到根本原因；二分查找、假说验证与埋点插桩都只是在消费该信号。若你没有这个信号，对着代码死盯再久也无济于事。

在此投入超常规的精力。**保持侵略性。保持创造力。绝不轻言放弃。**

### 构造反馈循环的方式——按以下大致顺序尝试

1. 在触及 Bug 的任意缝隙处编写**失败的测试用例**——单元测试、集成测试、端到端测试。
2. 针对正在运行的开发服务器执行 **Curl / HTTP 脚本**。
3. 传入固定 Fixture 输入的 **CLI 调用**，将 stdout 与已知良好的快照进行 Diff 对比。
4. **无头浏览器脚本** (Playwright / Puppeteer) —— 驱动 UI，针对 DOM / Console / 网络请求进行断言。
5. **重放捕获到的追踪记录 (Replay a captured trace)。** 将真实的生产网络请求 / Payload / 事件日志保存到本地磁盘；将其隔离重放到问题代码路径中。
6. **抛弃型脚手架。** 启动系统的最小子集（单个服务，Mock 外部依赖），通过单次函数调用即可触达 Bug 代码路径。
7. **属性测试 / Fuzz 循环。** 若 Bug 表现为“偶发错误输出”，跑 1000 次随机输入寻找失败模式。
8. **二分查找脚手架。** 若 Bug 出现在两个已知状态之间（Commit、数据集、版本号），自动化“在状态 X 下启动、检查、循环”，以便执行 `git bisect run`。
9. **差异对比循环 (Differential loop)。** 将同一份输入分别输入旧版本与新版本（或两种配置），对比两者的输出 Diff。
10. **人工闭环 (HITL) Bash 脚本。** 最后的兜底手段。若必须由人类点击，使用 `scripts/hitl-loop.template.sh` 来驱动*他们*，确保闭环依然结构化。捕获的输出反哺给你。

构建出正确的反馈循环，Bug 就已经解决了 90%。

### 紧凑化反馈循环 (Tighten the loop)

将这个循环视作一项产品。一旦你拥有了*一个*循环，**紧凑化**它：

- 我能否让它更快？（缓存前置准备、跳过无关初始化、缩小测试范围。）
- 我能否让信号更敏锐？（断言具体的异常症状，而非模糊的“未崩溃”。）
- 我能否让它更具确定性？（固定时间戳、设定随机数种子、隔离文件系统、冻结网络请求。）

一个耗时 30 秒且偶尔误报的循环并不比没有循环好多少；一个 2 秒且绝对确定性的循环则是极其强大的调试超能力。

### 非确定性 Bug (Non-deterministic bugs)

目标不是单次偶现，而是**提高复现概率**。将触发循环执行 100 次、并发多线程、施加高压、收紧时序窗口、注入 sleep。一个 50% 概率复现的 Bug 是完全可调试的；而 1% 则极其困难——持续提高复现概率直至其可被稳定调试。

### 确实无法构建循环时的应对

停下来并明确向用户说明。列出你尝试过的所有手段。请求用户提供：(a) 能够复现该问题的环境访问权限，(b) 脱敏后的捕获产物（HAR 文件、日志转储、Core Dump、带时间戳的录屏），或 (c) 允许在生产环境中添加临时埋点插桩。在没有建立循环之前，**切勿**直接进入猜想阶段。

### 完成准则 — 一个能够稳定飘红的紧凑循环

当循环满足**紧凑**且**具备飘红能力**时，阶段 1 宣告完成：你能够明确指出**一条单行命令**——脚本路径、测试调用、Curl 命令——且你已经**至少实际运行过一次**（展示调用及其脱敏输出），并满足：

- [ ] **具备飘红能力** — 驱动了真实的 Bug 代码路径并准确断言了**用户描述的精确症状**，从而在此 Bug 存在时必定飘红，修复后必定变绿。绝非“运行且不报错”——它必须能够*捕获这个特定 Bug*。
- [ ] **确定性** — 每次运行给出相同的判定结论（针对偶发 Bug：达到上述锁定的高复现率）。
- [ ] **快速** — 秒级，而非分钟级。
- [ ] **Agent 可自动运行** — 你可以在无人值守下独立运行；仅通过 `scripts/hitl-loop.template.sh` 引入人类闭环。

若你在拥有此命令之前就发现自己在翻看代码推导理论，**立即停下——直奔假说正是本技能旨在防止的典型失败模式。** 没有具备飘红能力的命令，就绝不进入阶段 2。

## 阶段 2 — 复现与最小化 (Reproduce + minimise)

运行循环。亲眼观察其飘红——Bug 浮现。

确认以下几点：

- [ ] 循环产出的故障模式正是**用户**所描述的现象——而非偶然出现在附近的无关错误。抓错 Bug = 治错病。
- [ ] 该故障在多次运行中稳定可复现（或对于非确定性 Bug，复现率已提升到足够开展调试的程度）。
- [ ] 你已精准捕获到具体的异常特征（错误信息、错误输出、耗时过长），以便后续阶段能够验证修复确实针对该症状生效。

### 最小化 (Minimise)

一旦飘红，将复现场景精简为**依然能够飘红的最小用例**。**一次削减一项**输入、调用方、配置、数据或步骤，每削减一项后重新运行循环——仅保留引发故障所必须的核心要素。

为何要精简：最小化的复现场景极大地收敛了阶段 3 的假说空间（剩下的可疑活动部件更少），并成为阶段 5 中干净的回归测试用例。

当**保留下来的每一个元素都是关键要素**时（移除其中任何一个都会使循环变绿），最小化完成。

在完成复现**且**最小化之前，切勿继续推进。

## 阶段 3 — 提出假说 (Hypothesise)

在验证任何假说之前，先生成 **3–5 个排序假说**。仅生成单个假说容易让人锚定在第一个看似合理的念头上。

每个假说都必须具备**可证伪性**：明确陈述其给出的预测。

> 格式标准：“如果 <原因 X> 是根因，那么 <修改 Y> 将使 Bug 消失 / <修改 Z> 将使 Bug 恶化。”

如果你无法陈述预测，该假说就只是一种直觉猜测——丢弃或将其打磨锐化。

**在开始测试前将排序列表展示给用户。** 用户通常具备能够瞬间重排优先级的领域知识（“我们刚刚给第 3 项上线了变更”），或者早已排除了某些假设。这是成本极低但收益巨大的时间节省点。无需死等回复——若用户暂时离开，按你自己的排序继续推进。

## 阶段 4 — 埋点插桩排查 (Instrument)

每个探针都必须对应阶段 3 中的具体预测。**一次只改变一个变量。**

工具优先级偏好：

1. 若环境支持，优先使用 **调试器 (Debugger) / REPL 检查**。一个断点胜过十条日志。
2. 在能够区分不同假说的代码边界处添加**针对性日志**。
3. 绝不要“打印所有日志然后 grep”。

为每条调试日志打上唯一前缀**标签**，例如 `[DEBUG-a4f2]`。这样最后的清理工作就简化为单次 grep。未打标签的日志容易残留；带标签的日志必定会被清理。

**性能排查分支。** 对于性能退化，日志通常具有误导性。应当：建立基准度量（耗时脚手架、`performance.now()`、Profiler 性能分析器、数据库执行计划），随后进行二分定位。先度量，后修复。

## 阶段 5 — 修复与回归测试 (Fix + regression test)

**在编写修复代码之前**先编写回归测试——但前提是存在**正确的缝隙**。

正确的缝隙是指测试能够完整还原在调用方处发生的**真实 Bug 模式**。若唯一可用的缝隙过于浅薄（当 Bug 需要多个调用方协作触发时只有单调用方测试，单元测试无法复现触发 Bug 的链条），在浅层编写的回归测试只会带来虚假的安全感。

**若不存在正确的缝隙，这本身就是一项重大发现。** 记录下来。这说明代码库的架构阻碍了 Bug 的有效锁定。将其标记留待下一阶段处理。

若存在正确的缝隙：

1. 将最小化的复现用例转化为该缝隙处的失败测试。
2. 亲眼观察其失败飘红。
3. 应用修复代码。
4. 亲眼观察其变绿通过。
5. 针对原始（未最小化）场景重新运行阶段 1 的反馈循环。

## 阶段 6 — 清理与复盘总结 (Cleanup + post-mortem)

在宣告完成前必须满足：

- [ ] 原始复现场景不再复现（重新运行阶段 1 的循环）
- [ ] 回归测试通过（或已记录缺乏正确缝隙的情况）
- [ ] 移除所有 `[DEBUG-...]` 埋点插桩（通过 grep 标签核对）
- [ ] 删除一次性抛弃型原型（或移至明确标记的调试归档目录）
- [ ] 在 Commit / PR 信息中明确阐明被证实的正确假说——以便未来的调试者学习

**最后反思：如何才能从根本上预防此类 Bug？** 若答案涉及架构调整（缺乏良好的测试缝隙、调用方关系混乱、隐藏的隐式耦合），将具体细节交接给 `/improve-codebase-architecture` 技能。请务必在修复完成**之后**提出建议，而非之前——此时你掌握的信息远比刚开始时更充分。
