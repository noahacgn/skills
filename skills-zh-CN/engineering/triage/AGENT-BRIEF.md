# 编写 Agent 任务任务书 (Writing Agent Briefs)

Agent 任务书是一份结构化的评论，在 GitHub Issue 或 PR 状态流转至 `ready-for-agent` 时发表。它是可供离线 AFK Agent 独立开展工作的权威规格契约。原始的正文和讨论记录是背景上下文，而 Agent 任务书是具备约束力的契约。

任务书明确说明了 **Agent 应当做什么**，适用于两种场景：对于 Issue，是从零构建变更；对于 PR，是针对*现有 Diff* 还需要做什么后续工作，补全实现、填补空白、解决评审意见。两者原则完全一致；下方的 PR 示例展示了具体差异。

## 编写原则

### 耐久性优于绝对精度 (Durability over precision)

Issue 可能会在 `ready-for-agent` 状态下停留数天或数周。期间代码库可能持续发生变动。编写任务书时，应确保即便文件被重命名、移动或重构，任务书依然保持有效。

- **应当** 描述接口、类型和行为契约
- **应当** 明确指出 Agent 应当寻找或修改的具体类型名、函数签名或配置形态
- **切勿** 引用具体文件路径，它们极易过时
- **切勿** 引用具体代码行号
- **切勿** 假定当前的代码实现结构将永远保持不变

### 面向行为，而非面向步骤流程 (Behavioral, not procedural)

描述系统应当**做什么**，而非**如何去实现**它。Agent 会重新自主探索代码库并做出自己的实现决策。

- **优秀：** “`SkillConfig` 类型应当支持接收一个可选的 `CronExpression` 类型的 `schedule` 字段”
- **糟糕：** “打开 src/types/skill.ts 并在第 42 行添加 schedule 字段”
- **优秀：** “当用户在不带任何参数的情况下运行 `/triage` 时，他们应当看到需要关注的 Issue 概览”
- **糟糕：** “在主处理函数中添加一个 switch 语句”

### 完备的验收准则 (Complete acceptance criteria)

Agent 需要清晰知晓何时宣告完工。每份 Agent 任务书都必须具备具体、可测试的验收准则。每条准则均应可独立验证。

- **优秀：** “运行 `gh issue list --label needs-triage` 能够返回已通过初始分类的所有 Issue”
- **糟糕：** “分类定级功能应当正常工作”

### 明确的范围边界 (Explicit scope boundaries)

明确声明哪些内容不在处理范围内。这能防止 Agent 画蛇添足过度设计，或对周边相邻功能做出无端假设。

## 模板

```markdown
## Agent Brief

**类别：** bug / enhancement
**摘要：** 一句话概括需要完成的任务

**当前行为：**
描述当前的运行状况。对于 Bug，即异常损坏的行为；
对于 Enhancement，即新功能所依托的现有现状。

**期望行为：**
描述 Agent 工作完成后的理想运行状态。
对边界极端情况和错误条件给出具体规范。

**核心接口：**
- `TypeName`：需要调整的内容及原因
- `functionName()` 返回类型，当前返回内容 vs 期望返回内容
- 配置结构，所需的新增配置选项

**验收准则：**
- [ ] 具体且可测试的准则 1
- [ ] 具体且可测试的准则 2
- [ ] 具体且可测试的准则 3

**不在范围内：**
- 本 Issue 中坚决不应改动或处理的事项
- 看似相关但实属独立的相邻功能
```

## 参考范例

### 优秀 Agent 任务书范例 (Bug)

```markdown
## Agent Brief

**类别：** bug
**摘要：** 技能描述截断发生在单词中间，导致输出破损

**当前行为：**
当技能描述超过 1024 个字符时，无论单词边界如何，均会在恰好 1024 字符处被生硬截断。
这导致描述往往以半个单词结尾（如 "Use when the user wants to confi"）。

**期望行为：**
截断应当在 1024 字符前的最后一个单词边界处发生，并追加 "..." 以表示截断。

**核心接口：**
- `SkillMetadata` 类型的 `description` 字段，类型本身无需修改，
  但为其填充数据的校验/处理逻辑需要支持识别单词边界
- 读取 SKILL.md Frontmatter 并提取描述的任何函数

**验收准则：**
- [ ] 1024 字符以内的描述保持原样不变
- [ ] 超过 1024 字符的描述在 1024 字符前的最后一个单词边界处截断
- [ ] 截断后的描述以 "..." 结尾
- [ ] 包含 "..." 在内的总长度不超过 1024 字符

**不在范围内：**
- 修改 1024 字符的长度上限本身
- 支持多行描述
```

### 优秀 Agent 任务书范例 (Enhancement)

```markdown
## Agent Brief

**类别：** enhancement
**摘要：** 新增 `.out-of-scope/` 目录支持以沉淀被否决的功能需求记录

**当前行为：**
当某个功能需求被否决时，Issue 会打上 `wontfix` 标签并附带评论关闭。
但没有针对该决策或背后理由的持久化记录。未来若出现类似请求，
需要维护者重新回忆或去搜索先前的讨论。

**期望行为：**
被否决的功能需求应当记录在 `.out-of-scope/<concept>.md` 文件中，
沉淀决策、根本原因以及请求该功能的所有 Issue 链接。
在对新 Issue 进行定级时，应当检索这些文件以查找匹配项。

**核心接口：**
- `.out-of-scope/` 中的 Markdown 文件格式，每个文件应当具备
  `# 概念名称` 标题、`**决策：**` 行、`**原因：**` 行以及附带 Issue 链接的 `**历史请求：**` 列表
- 分类定级工作流应当在早期阶段读取所有 `.out-of-scope/*.md` 文件，
  并按概念相似度对新到来的 Issue 进行匹配

**验收准则：**
- [ ] 将某个需求以 wontfix 关闭会在 `.out-of-scope/` 中创建/更新相应文件
- [ ] 文件包含决策、原因以及指向已关闭 Issue 的链接
- [ ] 若匹配的 `.out-of-scope/` 文件已存在，将新 Issue 追加到其“历史请求”列表中而非创建重复文件
- [ ] 在定级期间，当新 Issue 匹配到历史否决记录时能够检索并呈现已有 `.out-of-scope/` 文件

**不在范围内：**
- 自动化直接关闭匹配（需由人类确认匹配）
- 重新评估历史被否决的功能
- Bug 报告（仅需求改进的否决记录进入 `.out-of-scope/`）
```

### 优秀 Agent 任务书范例 (PR)

对于 PR，“当前行为”描述 Diff 的状态，任务书要求 Agent 补全或修复它，而非从零构建。

```markdown
## Agent Brief

**类别：** enhancement
**摘要：** 补全贡献者为 `triage list` 新增的 `--json` 输出参数

**当前行为：**
该 PR 添加了 `--json` 参数以将 Issue 列表序列化为 JSON。常规正常路径
运行良好，Diff 契合项目的命令结构。尚遗留两个缺口：错误信息仍以人类可读文本
形式打印（而非 JSON），且新参数缺乏测试覆盖。

**期望行为：**
当指定 `--json` 时，所有输出（包括错误信息）均在 stdout 上输出格式合法的 JSON，
且命令的退出码保持不变。未指定该参数时，原有的文本输出完全保持原样。

**核心接口：**
- 命令的错误处理路径在 `--json` 下应当输出 `{ "error": string }` 代替纯文本错误
- 复用 PR 已添加的现有序列化器；切勿引入第二个序列化器

**验收准则：**
- [ ] `triage list --json` 在成功和错误场景下均输出合法 JSON
- [ ] 退出码与非 JSON 命令完全一致
- [ ] 编写测试覆盖 `--json` 成功输出及一种错误场景
- [ ] 默认（非 JSON）输出在字节级别保持完全不变

**不在范围内：**
- 为任何其他命令添加 `--json`
- 修改 PR 已定义的成功 Payload 的 JSON 结构
```

### 糟糕的 Agent 任务书警示

```markdown
## Agent Brief

**摘要：** 修复定级功能中的 Bug

**要做的事情：**
定级功能坏了。看一下主文件并修好它。
大概在 150 行附近的函数有问题。

**需要修改的文件：**
- src/triage/handler.ts (第 150 行)
- src/types.ts (第 42 行)
```
