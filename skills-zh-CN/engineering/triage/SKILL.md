# 分类定级 (Triage)

推动项目 Issue 追踪系统中的 Issue 穿越由分类定级角色构成的轻量状态机。

若本仓库将外部 Pull Request 视为需求来源（参见 Issue 追踪系统配置），分类定级同样涵盖它们：**PR 本质上是附带了代码的 Issue**：相同的角色、相同的状态、相同的状态机，仅在下方标有“针对 PR”处有少量差异。根据配置将单纯的 `#42` 解析为 Issue 或 PR。

在分类定级期间发布到 Issue 追踪系统中的每一条评论或 Issue **必须**以该免责声明开头：

```
> *This was generated by AI during triage.*
```

## 角色体系 (Roles)

两个**分类角色 (Category)**：

- `bug`：某处功能损坏或异常
- `enhancement`：新功能或体验改进

五个**状态角色 (State)**：

- `needs-triage`：需要维护者进行评估
- `needs-info`：等待提交者补充更多信息
- `ready-for-agent`：规格明确完备，可供 AFK 离线 Agent 接手
- `ready-for-human`：需要人类工程师亲自编码实现
- `wontfix`：明确拒绝，不予处理

对于 PR，相同的状态对照其附带的代码理解：`ready-for-agent` 意味着已附带任务任务书，Agent 应接手推进该 Diff；`ready-for-human` 意味着已准备就绪可供人类合并。

每个完成定级的 Issue 应当携带且仅携带一个分类角色和一个状态角色。若状态角色产生冲突，立即标出并在开展任何动作前向维护者确认。

上述为规范角色名称，Issue 追踪系统中的实际标签字符串可能有所不同。映射关系应已配置。若未配置，请告知用户运行 `/setup-matt-pocock-skills`。

状态跃迁流向：未打标的 Issue 通常首先进入 `needs-triage`；随后流转到 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。一旦提交者回复，`needs-info` 重新回到 `needs-triage`。维护者随时可以覆盖状态，对看起来异常的跃迁进行标示并在推进前确认。

## 调用方式 (Invocation)

维护者调用 `/triage` 并以自然语言描述其诉求。理解诉求并执行操作。示例：

- “显示需要我关注的所有内容”
- “让我们看下 #42” (Issue 或 PR)
- “将 #42 移动到 ready-for-agent”
- “有哪些任务已经准备好让 Agent 接手了？”

## 展示待处理事项 (Show what needs attention)

查询 Issue 追踪系统并按时间由旧到新呈现三个分组：

1. **未打标 (Unlabeled)**：从未进行过定级。
2. **`needs-triage`**：评估正在进行中。
3. **自上次定级记录后提交者有新回复的 `needs-info`**：需要重新评估。

当 PR 在处理范围内时，将外部 PR 纳入这些分组，并在每行打上 `[PR]` 或 `[issue]` 标签。自动发现仅暴露*外部* PR（追踪配置定义了何为外部），协作者正在进行中的内部 PR 不属于定级范畴。该过滤仅用于自动发现；显式指定的 PR 无论作者是谁均可正常定级。

展示统计数量及每项的一行简述。由维护者进行挑选。

## 对特定 Issue 或 PR 进行分类定级

1. **收集上下文。** 通读完整的 Issue 或 PR（正文、评论、标签、作者、时间；对于 PR，还包括 Diff）。解析先前的定级记录，避免重复询问已解决的问题。使用项目的业务领域术语探索代码库，并遵循相关区域的 ADR。针对代码库执行两项检查：(a) **冗余性排查**：按业务概念（而非仅按请求的字面措辞）搜索该行为是否已有实现，并汇报搜索位置。若已存在，属于已实现的 `wontfix`（步骤 5）。(b) **历史否决排查**：阅读 `.out-of-scope/*.md`，指出与此请求相似的任何历史记录。

2. **给出建议。** 向维护者陈述你建议的分类与状态推荐及理由，并附带与该请求相关的简明代码库总结，包括是否已存在实现。等待维护者指令。

3. **验证事实依据 (Verify the claim)。** 在开展任何盘问之前，验证请求所述是否属实。对于 Bug，按照提交者的步骤尝试复现。对于 PR，确认 Diff 是否真正达成了其声称的效果，检出分支并运行相关测试或命令。汇报验证结果：已证实（附带代码路径）、复现失败、或细节不足（强烈的 `needs-info` 信号）。经过实证检验的结论能够支撑起更有力的 Agent 任务书。

4. **盘问打磨（按需）。** 若需求需要充实，调用 Skill 工具两次，分别传入 `"grilling"` 与 `"domain-modeling"`，通过逐轮提问将其打磨成型，提炼领域术语并在决策落地时就地更新 `CONTEXT.md` / ADR。

5. **落地执行定级结果：**
   - `ready-for-agent`：发表 Agent 任务任务书评论（参见 [AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human`：结构与 Agent 任务书相同，但注明为何无法委派给 AI（需要主观判断、外部权限、设计权衡、人工测试）。
   - `needs-info`：发表定级备忘（模板见下文）。
   - `wontfix`：关闭 Issue，评论根据*具体原因*定制：
     - **已实现**：该改动在代码库中已存在。指出其所在位置；**切勿**写入 `.out-of-scope/`（该知识库专用于*被否决*的需求，而非已实现的需求）。
     - **已否决 (Bug)**：礼貌解释原因，随后关闭。
     - **已否决 (需求改进)**：写入 `.out-of-scope/`，在评论中链接该文档，随后关闭（参见 [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage`：应用该角色。若有阶段性进展可附带可选评论。

## 快速状态覆盖 (Quick state override)

若维护者明确表示“将 #42 移动到 ready-for-agent”，信任维护者并直接应用该角色。确认即将执行的操作（角色变更、评论、关闭），随后执行。跳过盘问。若未经历盘问直接移动到 `ready-for-agent`，询问维护者是否需要起草 Agent 任务书。

## 补充信息备忘模板 (Needs-info template)

```markdown
## Triage Notes

**目前已明确的事项：**

- 要点 1
- 要点 2

**仍需您 (@reporter) 补充的信息：**

- 问题 1
- 问题 2
```

将盘问中已解决的所有内容记录在“已明确的事项”下，避免成果丢失。提出的问题必须具体且具备可操作性，切勿写成泛泛的“请提供更多信息”。

## 恢复先前会话

若 Issue 或 PR 上已存在先前的定级备忘，阅读它们，检查提交者是否已回答遗留问题，并在继续推进前呈现更新后的全貌。切勿重复询问已解答的问题。
