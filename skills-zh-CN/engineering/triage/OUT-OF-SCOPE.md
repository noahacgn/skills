# 超出范围知识库规范 (Out-of-Scope Knowledge Base)

代码库中的 `.out-of-scope/` 目录用于持久化保存被否决的功能需求记录。它承担两项核心使命：

1. **组织沉淀机制** — 记录为何否决某项功能，避免 Issue 关闭后背后的思考过程流失
2. **去重过滤机制** — 当新的 Issue 匹配到历史否决记录时，技能能够直接调出过往决策，避免重复拉扯争论

## 目录结构

```
.out-of-scope/
├── dark-mode.md
├── plugin-system.md
└── graphql-api.md
```

每个文件对应一个**业务概念 (concept)**，而非对应单个 Issue。请求相同特性的多个 Issue 统一归并到同一个文件中。

## 文件格式

文件应以轻松、易读的技术风格撰写——更像是一篇短小精炼的设计文档，而非冷冰冰的数据库条目。运用段落、代码示例与具体案例，使初次阅读者能够清晰理解其决策逻辑与深远考量。

```markdown
# 深色模式 (Dark Mode)

本项目暂不支持深色模式或面向用户的自定义主题切换。

## 为什么这属于超出范围 (Why this is out of scope)

渲染管道依赖于在 `ThemeConfig` 中定义的单套色彩体系。支持多套主题将需要：

- 包裹整个组件树的主题 Context Provider
- 针对每个组件的主题感知样式解析机制
- 用户主题偏好的持久化存储层

这是一项重大的架构调整，且与本项目聚焦于内容创作的核心初衷不符。主题定制应当由嵌入或二次分发输出内容的下游使用者负责。

```ts
// 当前的 ThemeConfig 接口在设计上并不支持运行时动态切换：
interface ThemeConfig {
  colors: ColorPalette; // 单一色彩配置，在构建时解析
  fonts: FontStack;
}
```

## 历史请求 (Prior requests)

- #42 — "添加深色模式支持"
- #87 — "出于无障碍考虑的夜间主题"
- #134 — "深色主题选项"
```

### 文件命名规范

为业务概念使用简短、描述性的 kebab-case 命名：`dark-mode.md`、`plugin-system.md`、`graphql-api.md`。命名应当具备足够高的辨识度，以便他人无需打开文件仅看文件名就能大致了解被否决的是什么。

### 编写否决原因

原因应当具备实质性内容——绝非简单的“我们不想要这个”，而是讲清楚“为什么”。优秀的理由通常涉及：

- 项目定位范围或哲学理念（“本项目专注于 X；主题化属于下游职责”）
- 技术架构约束（“支持该特性需要引入 Y，这与我们的 Z 架构相冲突”）
- 战略取舍决策（“出于……原因，我们选择使用 A 代替 B”）

原因应当经得起时间考验。避免提及临时性客观条件（“我们最近太忙了”）——那不叫真正的否决，那只是延期排期。

## 何时查阅 `.out-of-scope/`

在分类定级期间（步骤 1：收集上下文），通读 `.out-of-scope/` 下的所有文件。评估新 Issue 时：

- 检查该请求是否匹配已有的超出范围概念
- 匹配基于概念相似度，而非机械的关键词——“夜间主题”能准确匹配 `dark-mode.md`
- 若发现匹配，向维护者呈现：“这与 `.out-of-scope/dark-mode.md` 类似——我们先前因为 [原因] 否决了该需求。您目前依然持相同看法吗？”

维护者可能会：

- **确认否决** — 将新 Issue 追加到现有文件的“历史请求”列表中，随后关闭 Issue
- **重新考虑** — 删除或更新对应的超出范围文件，该 Issue 进入正常定级流程
- **判定不同** — 两个 Issue 虽相关但本质不同，按正常定级流程继续推进

## 何时向 `.out-of-scope/` 写入

仅当某个**需求改进 (enhancement)**（而非 Bug）被*明确否决*并打上 `wontfix` 时写入。这同样适用于需求类的 PR——被否决的 PR 记录在此，避免未来有人再次提交相同代码。

**切勿**因为某项功能**已经实现**而在此记录。已实现属于已完成功能，而非被否决功能；记录它会给去重机制造成错误干扰。对于已实现场景，直接在关闭评论中指出该功能目前所在的位置。

执行流转：

1. 维护者判定某个功能需求超出范围
2. 检查是否已存在匹配的 `.out-of-scope/` 文件
3. 若存在：将新 Issue 追加到“历史请求”列表
4. 若不存在：使用概念名称新建文件，包含决策、原因与首个历史请求
5. 在 Issue 上发表评论解释决策并提及 `.out-of-scope/` 文件
6. 为 Issue 打上 `wontfix` 标签并关闭

## 更新或删除超出范围文件

若维护者对先前否决的概念改变了主意：

- 直接删除对应的 `.out-of-scope/` 文件
- 技能无需重新打开旧 Issue——它们作为历史记录留存即可
- 触发本次重新审视的新 Issue 正常进入后续定级流程
