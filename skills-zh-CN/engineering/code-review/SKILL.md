针对 `HEAD` 与用户指定的固定基准点之间的 Diff 开展双维度审查：

- **规范维度 (Standards)**：代码是否符合本仓库记录的编码规范？
- **规格维度 (Spec)**：代码是否忠实实现了原始 Issue / Spec 的诉求？

两个维度分别作为**并行子 Agent** 独立运行，避免相互污染上下文，随后由本技能聚合其审查结果。

Issue 追踪系统应已配置完毕。若缺失 `docs/agents/issue-tracker.md`，请告知用户运行 `/setup-matt-pocock-skills`。

## 执行流程

### 1. 确定基准点 (Fixed point)

采用用户指定的任意基准点，Commit SHA、分支名、Tag、`main`、`HEAD~5` 等。若用户未明确指定，主动询问。

获取一次 Diff 比较基准：`git diff <fixed-point>...HEAD`（三点语法，以便基于 merge-base 展开对比）。同时通过 `git log <fixed-point>..HEAD --oneline` 记录 Commit 列表。

在进一步推进前，确认基准点能够正常解析（`git rev-parse <fixed-point>`）且 Diff 非空。无效的引用或空的 Diff 应当在此处直接拦截报错，而非在后续两个并行子 Agent 内部失败。

### 2. 识别规格来源 (Spec source)

按以下顺序查找原始规格说明：

1. Commit 提交信息中的 Issue 引用（`#123`、`Closes #45`、GitLab `!67` 等），通过 `docs/agents/issue-tracker.md` 中的工作流获取。
2. 用户作为参数传入的文件路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名或功能匹配的 Spec 文件。
4. 若均未找到，向用户询问 Spec 所在位置。若用户确认不存在，**规格 (Spec)** 子 Agent 将跳过并汇报“无可用规格说明”。

### 3. 识别规范来源 (Standards sources)

仓库中记录代码编写要求的任何文档，例如 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`。

除了仓库自身记录的规范外，规范维度始终附带下方的**坏味道基准 (smell baseline)**：这是一组固定的 Fowler 代码坏味道规则（《重构》第 3 章），即使仓库未记录任何规范也依然适用。其受两条规则约束：

- **仓库规范优先。** 仓库已记录的规范具有最高优先级；若其明确支持基准会标出的某种模式，则抑制该坏味道报警。
- **始终属于主观判断。** 每个坏味道都是一条带有明确标签的启发式参考（如“疑似 Feature Envy”），绝非硬性违规，并且与此处的任何标准一样，跳过已由 linter 等自动化工具强制执行的项。

每个坏味道条目按照*定义* → *修复方式*展开；对照 Diff 进行匹配：

- **神秘命名 (Mysterious Name)**：函数、变量或类型的名称未能揭示其职责或承载的内容。→ 重命名；若想不出恰如其名的好名字，说明设计本身存在模糊之处。
- **重复代码 (Duplicated Code)**：相同的逻辑结构出现在变更中的多个代码块或文件中。→ 提炼公共逻辑，在两处共同调用。
- **依恋情结 (Feature Envy)**：某个方法频繁访问另一个对象的数据，超过对自己数据的访问。→ 将该方法移动到它所依恋的数据所在对象中。
- **数据泥团 (Data Clumps)**：同样的几个字段或参数总是一起出现（预示着一个新类型呼之欲出）。→ 将其打包为单一结构体/类型并统一传递。
- **基本类型偏执 (Primitive Obsession)**：使用基本类型或字符串指代本应拥有独立类型的业务领域概念。→ 为该概念赋予专属的轻量类型。
- **重复的 Switch/If 级联 (Repeated Switches)**：针对同一类型的相同 `switch`/`if` 级联在变更中多处重现。→ 替换为多态模式，或由两处共享的单一映射表。
- **发散式霰弹修改 (Shotgun Surgery)**：单一逻辑变更迫使 Diff 中分散修改了大量文件。→ 将总是协同变化的内容聚合到单个模块中。
- **发散式变化 (Divergent Change)**：单个文件或模块因多个互不相关的理由被修改。→ 拆分模块，确保每个模块只因单一原因而变更。
- **夸夸其谈未来性 (Speculative Generality)**：为 Spec 并不存在的需求预先添加抽象、参数或钩子。→ 果断删除；在真实需求显现前保持内联简单实现。
- **过长消息链 (Message Chains)**：调用方依赖诸如 `a.b().c().d()` 的过长链式导航。→ 将链式遍历封装在首个对象的单一方法之后。
- **中间人 (Middle Man)**：某个类或函数的大部分工作仅仅是向下透传委托。→ 剔除中间人，直接调用真正目标。
- **被拒绝的遗赠 (Refused Bequest)**：子类或实现类忽略或覆盖了其继承的大部分内容。→ 放弃继承，改用组合（Composition）。

### 4. 并行启动两个子 Agent

**规范维度 (Standards) 子 Agent Prompt**：包含：

- 完整的 Diff 命令与 Commit 列表。
- 步骤 3 中找到的规范文件列表，**外加步骤 3 的坏味道基准原文**：子 Agent 无法通过其他途径获取该基准。
- 任务指引：“请针对相关文件/代码块汇报：(a) Diff 中违反已记录规范的每一处：注明规范来源（文件 + 具体规则）；(b) 你发现的任何基准坏味道：命名该坏味道并引用代码块。严格区分硬性违规与主观判断，违反已记录规范可能是硬性的，但基准坏味道始终属于主观启发式判断，且仓库记录的规范优先于基准。跳过工具链已强制检查的内容。篇幅控制在 400 字以内。”

**规格维度 (Spec) 子 Agent Prompt**：包含：

- Diff 命令与 Commit 列表。
- Spec 的文件路径或抓取到的正文内容。
- 任务指引：“请汇报：(a) Spec 要求的核心需求中存在缺失或未完整实现的部分；(b) Diff 中超出 Spec 要求的不必要行为（范围蔓延）；(c) 表面看似已实现但具体实现逻辑有误的项。对每项发现引用 Spec 原文行。篇幅控制在 400 字以内。”

若 Spec 缺失，跳过规格子 Agent 并在最终报告中注明。

### 5. 聚合呈现

在 `## 规范维度 (Standards)` 和 `## 规格维度 (Spec)` 标题下并排呈现两份报告，保持原文或进行轻微格式整理。**切勿**合并或交叉重排两边的结论，这两个维度特意保持独立（参见下文*为何采用双维度*）。

以单行摘要收尾：每个维度的总发现数，以及*各维度内部*最严重的问题（若存在）。不要在跨维度之间挑选出唯一的综合结论，这正是双维度隔离设计旨在避免的重排干扰。

## 为何采用双维度

一项代码变更完全可能在一个维度表现优异而在另一个维度遭遇滑铁卢：

- 完全遵循每条规范但实现了错误业务逻辑的代码 → **规范通过，规格失败。**
- 严格达成了 Issue 的全部要求但破坏了项目代码约定的代码 → **规格通过，规范失败。**

独立汇报两个维度可以防止一个维度的表现掩盖另一个维度的问题。
